# bfemu — виртуальный полётный контроллер Betaflight (MSP + CLI)

Эмулятор полётного контроллера, к которому **Betaflight Configurator подключается как к настоящему FC**:
проходит рукопожатие, читает телеметрию, настраивает параметры и **работает с полной командной строкой (CLI)** —
и через MSP (`MSP2_CLI_COMMAND`), и через «сырой» CLI-порт (`#`, эхо, приглашение `# `).

Внутри — только стандартная библиотека Python 3.10+, никаких зависимостей.

```
$ python3 -m bfemu --tcp 127.0.0.1:5761 --http 8088
#   ↑ без --http MSP-порт работает, но веб-страниц нет: эмулятор скажет об этом в логе.
#     Веб-порт занят? Возьмём следующий свободный и напечатаем настоящий адрес.
[FC] Betaflight 4.5.4 / MSP API 1.46.0 / настроек в базе: 683
[TCP] виртуальный FC слушает 127.0.0.1:5761
```

## Что эмулируется

| Слой | Что реализовано |
|---|---|
| Транспорт MSP | кадры v1 (`$M<`) и v2 (`$X<`), CRC XOR и CRC8-DVB-S2, потоковый парсер с ресинхронизацией |
| Рукопожатие | `MSP_API_VERSION` → `MSP_FC_VARIANT` (BTFL) → `MSP_FC_VERSION` → `MSP_BUILD_INFO` (+ build-опции прошивки) → `MSP_BOARD_INFO` → `MSP_STATUS` → `MSP_UID` → `MSP2_GET_TEXT` → `MSP_SET_RTC` — ровно как в `serial_backend.js` |
| Телеметрия | `MSP_ANALOG`, `MSP_BATTERY_STATE`, `MSP_ATTITUDE`, `MSP_ALTITUDE`, `MSP_RAW_IMU`, `MSP_RC`, `MSP_MOTOR`, `MSP_RAW_GPS`, `MSP_COMP_GPS`, `STATUS/STATUS_EX`, `MSP_MOTOR_TELEMETRY` (значения «живые»: синусоиды, просадка батареи, расход mAh) |
| Настройки | 683 реальные настройки Betaflight 4.5.4 с типами, диапазонами и списками значений (сгенерированы из исходников прошивки) |
| CLI | `help`, `version`, `status`, `tasks`, `get`, `set`, `dump`, `diff`, `defaults`, `save`, `exit`, `feature`, `beeper`, `serial`, `aux`, `mixer`, `map`, `resource`, `timer`, `dma`, `board`, `mcu_id`, `uid`, `flash_info`, `batch`, `bl`, `vtx`, `servo`, `smix`, `gpspassthrough` — и все остальные команды `cmdTable[]` прошивки 4.5.4 (`profile`, `rateprofile`, `rxfail`, `rxrange`, `adjrange`, `motor`, `mmix`, `dshotprog`, `dshot_telemetry_info`, `led`, `color`, `mode_color`, `play_sound`, `flash_read`/`flash_write`/`flash_erase`/`flash_scan`, `sd_info`, `signature`, `bind_rx`, `rc_smoothing_info`, `simplified_tuning`, `escprog`, `gyroregisters`, `serialpassthrough`…), плюс `battery_profile` из мастера BF и эмуляторные `blackbox`, `board`, `osd_layout`, `uid`,
`sim_flight` (живое питание) + автодополнение по TAB |
| CLI через MSP | `MSP2_CLI_COMMAND` (0x3012) с пейджингом, `MSP2_CLI_SETTING` (0x3010), `MSP2_CLI_SETTING_INFO` (0x3011) |
| Поведение | `save`/`exit`/`defaults`/`MSP_SET_REBOOT` рвут линк и поднимают его заново |
| «Флеш» (EEPROM) | `MSP_EEPROM_WRITE` и CLI `save`/`defaults` пишут конфигурацию в `eeprom.json`; при старте и после каждой перезагрузки она оттуда поднимается — настройки живут между запусками эмулятора |

Идентичность по умолчанию: **Betaflight 4.5.4, MSP API 1.46, MCU F405, плата S405**, variant `BTFL`.
Меняется флагами `--fc-version` и `--api-version`.

## Быстрый старт

```bash
cd bfemu
python3 -m bfemu --tcp 127.0.0.1:5761 --http 8088   # TCP для Configurator + веб-монитор состояния
python3 tools/demo_session.py                        # пример «клиента-Configurator» в терминале
```

Веб-монитор по умолчанию слушает только **127.0.0.1** (на странице `/tx` двигаются стики — в общей
сети это значит «любой сосед управляет вашим FC»). MSP-порт ведёт себя так же: без `--tcp` адрес
`127.0.0.1:5761`, потому что по нему пишется конфигурация, гоняются моторы и принимаются каналы
управления. Нужен доступ с планшета или другой машины — открывайте оба адреса явно:

```bash
python3 -m bfemu --tcp 0.0.0.0:5761 --http 8088 --http-host 0.0.0.0
```

Без `--tcp` эмулятор поднимается на `127.0.0.1:5761` — этого достаточно для Configurator на той же
машине (`tcp://127.0.0.1:5761`).

## Как подключить Betaflight Configurator

1. **Настольное приложение (Windows/macOS/Linux)** — самый простой путь:
   включите *Manual connection* (ручное подключение), в поле порта введите
   `tcp://127.0.0.1:5761` → **Connect**.

   > В браузерной PWA-версии Configurator TCP-подключение недоступно (браузер не умеет открывать
   > сырые сокеты в произвольный порт). Нужно именно настольное приложение, сборка Tauri.

2. **Linux/macOS через псевдотерминал** (Configurator видит обычный последовательный порт):

   ```bash
   python3 -m bfemu --pty /tmp/ttyBFEMU
   # затем в Configurator выберите порт /tmp/ttyBFEMU
   ```

3. **Windows**: либо пункт 1 (TCP), либо связать наш `--stdio` с виртуальной парой COM-портов
   (`com0com`, `hub4com`) или `socat`-мостом.

После подключения доступны рукопожатие, вкладки настроек, телеметрия и **вкладка CLI**
(вход по `#`, эхо символов, приглашение `# `, `dump`, `diff all`, `set`, `save`).

## Откуда берутся настройки

`tools/gen_data.py` разбирает дерево исходников Betaflight:

```bash
git clone --depth 1 --branch 4.5.4 https://github.com/betaflight/betaflight /tmp/bf454
python3 tools/gen_data.py /tmp/bf454
```

Что извлекается:

* `src/main/cli/settings.c` → таблица `valueTable[]` (имя, тип, секция `master/profile/rateprofile`,
  режим, диапазон или список значений, PG-группа) — 683 настройки;
* `pgResetFn_*` / `PG_RESET_TEMPLATE` → заводские значения (317 настроек распознаются автоматически,
  остальные берутся из `fc_overrides.json` или эвристики);
* `msp_box.c` → боксы AUX (`MSP_BOXNAMES`/`MSP_BOXIDS`) с их `permanentId`;
* `cli.c` → имена фич, функции последовательных портов; `settings.h` → таблицы lookup-значений
  (то, что печатается как `Allowed values:`).

## Тонкости формата MSP, на которых легко ошибиться

Проверено по исходникам Betaflight 4.5.4 и Betaflight Configurator 2026.6:

* **Строки в `MSP_BOARD_INFO` и `MSP2_GET_TEXT` — с префиксом длины**, а не C-строки:
  `sbufWriteU8(dst, strlen(name)); sbufWriteData(dst, name, strlen(name));`
  Configurator читает их через `getText()` = «байт длины + символы». Если записать
  `name\0`, он примет первый символ имени за длину и покажет мусор (в UI — «квадратики»).
* **`MSP_NAME`** — наоборот, просто символы без длины и без завершающего нуля.
* **Маска активных сенсоров в `MSP_STATUS`/`STATUS_EX`** упаковывается в `msp.c` в порядке
  `acc<<0 | baro<<1 | mag<<2 | gps<<3 | rangefinder<<4 | gyro<<5` — это НЕ порядок из
  `sensors.h`. Configurator (`have_sensor`) понимает именно такую упаковку: если бит GPS не
  выставлен, он не запросит `MSP_RAW_GPS`, и GPS в UI останется нулевым.
* **`MSP_STATUS_EX` (API 1.46)** = 24 байта: cycleTime, i2cError, sensors, modeFlags,
  pidProfile, cpuLoad, PID_PROFILE_COUNT, rateProfile, byteCount(+байты флагов),
  `ARMING_DISABLE_FLAGS_COUNT` (26), armingFlags (u32), configStateFlags (u8), cpuTemp (u16).
  Флаг «ARM_SWITCH» — это `1 << 25`, а `1 << 0` — это `NO_GYRO` (частый источник надписи
  «NO_GYRO» в Setup при живом гироскопе).
* **Подпись платы** — 32 нулевых байта, когда сборка без `USE_SIGNATURE` (как на стоковой прошивке).
* **Вкладка «Порты»** в 2026.x читает порты через `MSP2_COMMON_SERIAL_CONFIG` (**0x1009**, а не 0x1008!) и
  пишет через `MSP2_COMMON_SET_SERIAL_CONFIG` (0x100A). Формат: `count u8`, далее по 9 байт на порт —
  `identifier u8, functions u32, msp/gps/telemetry/blackbox baud u8`. Идентификаторы портов —
  из `serialPortIdentifier_e`: UART1..UART10 = 0..9, VCP = 20, SOFTSERIAL1/2 = 30/31.
  **Порядок строк — как в прошивке**, а не «как удобно»: массив `serialPortIdentifiers[]`
  (`src/main/io/serial.c`) начинается с `SERIAL_PORT_USB_VCP`, и в этом же порядке порты уходят
  в `MSP_SERIAL_CONFIG`/`MSP2_COMMON_SERIAL_CONFIG` и в CLI-дамп `serial`
  (`serial 20 1 115200 57600 AUTO 115200` идёт первым). Configurator строки не сортирует —
  рисует как пришли (`usePortsState.js`), поэтому **USB VCP в таблице первый**, а за ним UART1…UART5.
  Скорости — заводские, как в `pgResetFn_serialConfig()`: MSP 115200, датчики/GPS 57600,
  телеметрия AUTO, «чёрный ящик» 115200.
  Перед этим вкладка ждёт `MSP_VTX_CONFIG`, поэтому его ответ тоже обязан быть полным (15 байт).
* **`MSP_VTX_CONFIG`** (API 1.42+) = 15 байт: type, band, channel, power, pitMode (u8),
  frequency (u16), deviceReady, lowPowerDisarm (u8), pitModeFrequency (u16),
  tableAvailable, tableBands, tableChannels, tablePowerlevels (u8).

## Ограничения (честно)

* Реализованы не все MSP-коды. Неизвестные запросы **не игнорируются молча**: эмулятор отвечает
  пустым payload, чтобы Configurator не ждал таймаут, и пишет код в лог (`--quiet` отключает).
  Список «чего не хватает» удобно смотреть по логу веб-монитора.
* Отдельные вкладки (OSD-раскладка, LED, пресеты) отдают сокращённый, но структурно совместимый
  ответ — их можно дорабатывать обработчик за обработчиком. «Сервоприводы» отдают полный набор
  (8 сервоприводов + 16 правил микшера) и сохраняются во «флеш».
* `dump` печатает обычные (`DIRECT`/`LOOKUP`) настройки; массивы (`MODE_ARRAY`) и битсеты пока
  пропускаются.
* Это не симулятор физики полёта: значения датчиков синтетические. Моторы «крутятся» только в тесте
  на вкладке «Моторы» — обороты, ток ESC, нагрев и просадка питания считаются по модели, похожей на
  поведение прошивки, а не снимаются с настоящих ESC.

## Как включить SOFTSERIAL и увидеть его во вкладке «Порты»

Как на настоящем FC: софт-серийные порты **не показываются, пока фича выключена**. Прошивка
(`serial.c`, `serialPortUsageList`) убирает их из списка доступных, если `softserialEnabled == false`
или не назначены пины; Configurator рисует строки ровно по тому, что прислал FC.

Порядок действий:

1. **Конфигурация** → включить **SOFTSERIAL** → **Сохранить и перезагрузить**.
   В логе: `[MSP] фичи сохранены: ... SOFTSERIAL` и `[FC] фича SOFTSERIAL: добавлены порты SOFTSERIAL1/2`.
2. Дождаться переподключения и открыть **Порты** — в таблице появятся строки
   `SOFTSERIAL1` и `SOFTSERIAL2` (это идентификаторы 30 и 31, как в `serialPortIdentifier_e`).
3. Выключить фичу — строки исчезнут.

Проверить со стороны FC, не заходя в интерфейс:

```bash
python3 tools/check_softserial.py     # весь сценарий: включение, перезапуск, список портов
curl http://127.0.0.1:8088/api/state  # "ports": [... {"name": "SOFTSERIAL1", ...}]
```

В `MSP_BOARD_INFO` эмулятор отдаёт `targetCapabilities = 0x03` — VCP (бит 0) и HAS_SOFTSERIAL (бит 1),
как прошивка с `USE_VCP`/`USE_SOFTSERIAL`. По этому биту Configurator понимает, что сборка умеет
софт-серийные порты (`fc.js: boardHasSoftSerial`).

## Сохранение изменений, сделанных в интерфейсе Configurator

Вкладки пишут конфигурацию **не только** через CLI-настройки — у них есть прямые MSP-запросы
(`MSP_SET_SENSOR_CONFIG`, `MSP_SET_RX_CONFIG`, `MSP_SET_PID` и т.д.). Эмулятор их разбирает и
сохраняет в «флеш»:

| Код записи | Что это | Код чтения |
|---|---|---|
| 97 | выбор железа датчиков (вкладка «Датчики») | 96 |
| 37 / 11 / 65 | фичи, имя дрона, карта каналов | 36 / 10 / 64 |
| 62 | ARMING_CONFIG — это те же значения, что настройки `auto_disarm_delay`/`small_angle` | 61 |
| 33, 43, 45, 51, 76, 185, 217, 220, 223, 224, 225 | конфигурации батареи, микшера, приёмника, RSSI, failsafe, пищалки, 3D-газа, выравнивания датчиков, GPS, компаса, GPS Rescue | 32, 42, 44, 50, 75, 184, 124, 126, 132, 133, 135 |
| 202 / 95 / 204 / 93 / 218 / 222 / 91 | PID, PID Advanced, Rates, фильтры, дедбенды, параметры моторов, «Конфигурация» — разбираются **по смыслу** (вкладки «PID настройки» и «Моторы») | 112, 94, 111, 92, 125, 131, 90 |

Ответы `112` (PID), `94` (PID Advanced), `111` (Rates), `92` (фильтры), `125` (дедбенды) и `131`
(параметры моторов) не «подставляются из записанного», а **собираются из настроек** — тех же, что
видит CLI. Иначе вкладка «PID настройки» показывала бы одно, а `get p_roll` и вкладка «Моторы» —
другое. Для остальных пар эмулятор страхуется: если размер записанного payload не совпадает с
генерируемым ответом, отдаётся сгенерированный (испортить разбор данных невозможно).

Что важно: как и на настоящем FC, изменения в интерфейсе применяются к «RAM» сразу, а во «флеш»
попадают только по кнопке **Save / Save and Reboot** (или `save` в CLI). Если закрыть Configurator
без сохранения — изменения loss, как и в железе.

## Биты фич: почему SOFTSERIAL — это 1 << 6

В прошивке фичи нумеруются **с пропусками** (`feature.h`):

```c
FEATURE_RX_PPM           = 1 << 0,
FEATURE_INFLIGHT_ACC_CAL = 1 << 2,
FEATURE_RX_SERIAL        = 1 << 3,
FEATURE_SOFTSERIAL       = 1 << 6,   // биты 1, 8, 11, 19, 23, 24, 26, 29 — пустые
FEATURE_GPS              = 1 << 7,
FEATURE_LED_STRIP        = 1 << 16,
FEATURE_OSD              = 1 << 18,
FEATURE_AIRMODE          = 1 << 22,
FEATURE_ANTI_GRAVITY     = 1 << 28,
```

Configurator (`src/js/Features.js`) использует ровно эти же биты. Поэтому нумеровать фичи
«по порядку непустых имён» нельзя: получается сдвиг (SOFTSERIAL вместо бита 6 попадает в 5,
GPS — в 6), галочка в интерфейсе включает чужую фичу, и, например, порты SOFTSERIAL1/2 не
появляются. `gen_data.py` берёт биты из позиций массива `featureNames[]` в `cli.c`, а эмулятор
при старте сверяет их (`check_feature_bits()`) и предупреждает в логе при расхождении.

## Фичи и порты SOFTSERIAL

Фичи (`MSP_FEATURE_CONFIG` / `MSP_SET_FEATURE_CONFIG`, вкладка «Конфигурация») сохраняются во «флеш»
и переживают перезапуск. Битовая маска берётся из `featureNames[]` прошивки (22 фичи, порядок бит
совпадает с `FEATURE_*` в `feature.h`).

Отдельный случай — **SOFTSERIAL**: это не просто флаг. Прошивка собрана с `USE_SOFTSERIAL`, поэтому
при включении фичи в списке портов появляются `SOFTSERIAL1`/`SOFTSERIAL2` (идентификаторы 30/31),
а при выключении — исчезают. Эмулятор повторяет это: во вкладке «Порты» строки появляются и
пропадают вслед за галочкой.

В CLI команда `feature` работает как в прошивке:

```
feature            -> Enabled: RX_SERIAL TELEMETRY OSD AIRMODE ANTI_GRAVITY
feature list       -> Available: RX_PPM INFLIGHT_ACC_CAL RX_SERIAL ... (все фичи сборки)
feature LED_STRIP  -> Enabled
feature -SOFTSERIAL-> Disabled   (и порты SOFTSERIAL1/2 убираются)
```

## Сохранение конфигурации («флеш»)

Эмулятор ведёт себя как настоящий FC: пока вы не нажали **Save** / **Save and Reboot**,
изменения живут только в RAM и теряются при перезагрузке или выходе из CLI (`exit`).

| Действие | Что происходит |
|---|---|
| `MSP_EEPROM_WRITE` (кнопка **Save** в любой вкладке) | конфигурация пишется в `eeprom.json` |
| CLI `save` | запись + перезагрузка (`save noreboot` — без перезагрузки) |
| CLI `defaults` | сброс всей конфигурации к заводским (настройки, фичи, порты, микшер, датчики,
слоты `vtx`) + запись + перезагрузка (`defaults nosave` — только в RAM) |
| CLI `exit` | несохранённые изменения теряются |
| `MSP_RESET_CONF` | то же, что `defaults`, но с MSP: сброс + запись во «флеш» + перезагрузка (как `resetEEPROM()` в config.c) |
| Перезагрузка (`MSP_SET_REBOOT`, `save`, `Reboot`) | конфигурация поднимается из «флеша» |

Что попадает в файл: все 683 настройки (включая батарейные — `vbat_*`, `bat_capacity`,
`battery_meter`, `current_meter`, калибровку `vbat_scale`/`ibata_scale`), фичи, конфигурация портов, AUX-режимы, имена дрона/пилота/платы,
имена профилей и UID (поэтому Configurator узнаёт то же устройство после перезапуска).

```bash
python3 -m bfemu --tcp 127.0.0.1:5761 --http 8088          # «флеш» = <папка проекта>/eeprom.json
python3 -m bfemu ... --eeprom C:\bfemu\my-fc.json          # свой файл
python3 -m bfemu ... --eeprom none                          # только память, как раньше
python3 -m bfemu ... --wipe                                 # стереть «флеш» и стартовать с заводских
```

Сбросить состояние вручную:

| Способ | Что делает |
|---|---|
| удалить `eeprom.json` при остановленном эмуляторе | при следующем запуске — заводские настройки (`«флеш» пусто`) |
| удалить файл при работающем эмуляторе | действует со следующей перезагрузки FC; файл пересоздастся только при следующем сохранении |
| `python -m bfemu --wipe` | стирает «флеш» и стартует с заводских |
| `python -m bfemu --eeprom none` | выключает «флеш» совсем: изменения живут до выхода |
| кнопка **«Сбросить настройки»** в Setup (MSP_RESET_CONF) | сброс к заводским **с записью** в «флеш» + перезагрузка |

## Полезно знать про CLI

* Вход в CLI из Configurator — один байт `#`; в ответ прошивка печатает
  `\r\nEntering CLI Mode, type 'exit' to reboot, or 'help'\r\n# `.
* `MSP.send_cli_command` (пакетный режим) работает иначе: клиент шлёт `STX (0x02) + команда + LF + ETX (0x03)`,
  а прошивка отвечает текстом, обрамлённым `STX … ETX`.
* Команды `save`, `exit`, `defaults` перезагружают FC: линк рвётся и поднимается снова
  (в TCP-режиме слушающий сокет остаётся, Configurator переподключается сам).
* Ошибки формата 4.5.4: `###ERROR IN set: gyro_lpf1_static_hz NOT BETWEEN 0 AND 1000`,
  `###ERROR IN input: UNKNOWN COMMAND, TRY 'HELP'`, `ERR_CMD_NA: <строка>` (неинтерактивный режим).
* **Строковые параметры** (`MODE_STRING`: `craft_name`, `pilot_name`, `profile_name`,
  `rateprofile_name`, `osd_profile_N_name`, `box_user_N_name`, `gps_nmea_custom_commands`)
  задаются строкой, а не числом — как в прошивке:

  ```
  # set craft_name=qqq              → принимается (до 16 символов)
  # set craft_name=0123456789ABCDEFG
  ###ERROR IN set: STRING MUST BE 1-16 CHARACTERS OR '-' FOR EMPTY
  # set craft_name=-
  # get craft_name
  craft_name = -
  String length: 1 - 16
  ```

  У `craft_name`/`pilot_name` предел 16 символов (config.h `MAX_NAME_LENGTH`), у
  `profile_name`/`rateprofile_name` — 8, у `box_user_N_name` — 8, у `osd_profile_N_name` — 16,
  у `gps_nmea_custom_commands` — 64 (те же числа, что в `cli/settings.c` 4.5.4). `-` (emptyName)
  стирает значение. Имя дрона — то же поле, что пишет вкладка «Конфигурация»
  (`MSP_SET_NAME`/`MSP2_SET_TEXT`): `set craft_name=…` видно в Configurator, а имя из вкладки —
  в `get`/`dump`. Строки лежат в «флеше» рядом с остальными настройками и переживают
  `save` и перезапуск; в `dump` имя печатается строкой `# name: qqq`.

## Вкладка «GPS»: приёмник на UART1 и живой фикс

Configurator показывает вкладку **«GPS»** только если прошивка сообщила build-опцию `USE_GPS`
(в исходниках приложения это `src/components/sidebar/sidebar_items.js`:
`{ key: "gps", ... buildOptions: ["USE_GPS"] }`). Эмулятор её сообщает — код 16412 в
`MSP_BUILD_INFO`, рядом с `USE_SERVOS`/`USE_LED_STRIP`.

Что при этом видно во вкладке:

* **протокол UBLOX** (`gps_provider = 1`), SBAS, авто-настройка модуля, Galileo, «точка дома один раз» —
  читаются из `MSP_GPS_CONFIG` (6 байт) и пишутся обратно тем же кодом `MSP_SET_GPS_CONFIG`,
  поэтому кнопка «Сохранить» во вкладке работает и переживает перезапуск;
* **живое решение**: `MSP_RAW_GPS` (fix = `STATE(GPS_FIX)`, 9–10 спутников, широта/долгота,
  высота, скорость, курс в 0.1°, pdop), `MSP_COMP_GPS` (дистанция и направление до дома),
  `MSP_GPSSVINFO` (**24 спутника**: система, номер, качество с битом «используется», C/N0);
* **спутников больше 16 — и это важно**: Configurator (`GpsTab.vue`) включает подробную таблицу
  сигналов (имена систем в колонке Gnss ID, зелёные метки «используется», подписи качества
  вида «поиск» / «отслеживается» / «полностью отслеживается») только когда спутников **больше
  шестнадцати**; при 16 и меньше рисуется упрощённый список — прочерки в Gnss ID, числовое
  качество и все метки красные. У настоящего мульти-GNSS модуля видно 20–30 спутников сразу
  (GPS + SBAS + Galileo + BeiDou + Glonass), поэтому и у нас 24;
* строки **«Использовать Галилео»** и **«Тип коррекции спутниковых координат»** вкладка
  показывает только при включённой «Автонастройке» (так устроен её шаблон:
  `showAutoConfig = provider === UBLOX`, а от него зависят `showUbloxGalileo`/`showUbloxSbas`);
* координаты медленно «ходят» вокруг базовой точки (радиус 25 м, ~0.7 м/с), поэтому карта,
  спидометр и курс во вкладке обновляются, а не стоят на месте;
* переключатель **GPS** во вкладке — это обычная фича (бит 7, `feature GPS`); она включена с завода,
  потому что на виртуальной плате действительно есть GPS-модуль на UART1 (см. «Порты») и датчик GPS
  в `MSP_STATUS`;
* имена настроек в CLI — те же: `get gps_provider`, `get gps_sbas_mode`, `get gps_ublox_use_galileo`.

Проверка разом:

```
python3 tools/check_gps_tab.py
```

## Вкладка «ВИДЕОПЕРЕДАТЧИК»: передатчик и таблица частот

Эмулятор ведёт себя как плата с TBS SmartAudio на UART4 (функция включена в конфигурации портов
по умолчанию — как на скриншотах из Configurator):

| Запрос | Код | Что отдаёт |
|---|---|---|
| `MSP_VTX_CONFIG` | 88 | 15 байт: тип устройства, банд/канал/мощность, pit-режим, частота, готовность, признак наличия таблицы и её размеры |
| `MSP_VTXTABLE_BAND` | 137 | имя банда, буква, флаг `FACTORY`, частоты всех каналов |
| `MSP_VTXTABLE_POWERLEVEL` | 138 | значение уровня в мВт и подпись |
| `MSP_SET_VTX_CONFIG` | 89 | выбор банда/канала/частоты, мощности, pit-режима, размеров таблицы и её очистка |
| `MSP_SET_VTXTABLE_BAND` / `…POWERLEVEL` | 227 / 228 | запись строк таблицы (имена и подписи — в верхний регистр, как в прошивке) |
| `MSP2_GET_VTX_DEVICE_STATUS` | 0x3004 | состояние передатчика: тип, готовность, банд/канал, индекс мощности, частота, флаги (pit-режим), уровни «dBm → мВт» и паспорт SmartAudio (версия 2.1, режим, частота pit) |

Важные детали:

* **Таблица заполнена с завода.** Эмулятор стартует как BNF-квад, у которого производитель уже
  залил таблицу: 5 полос (BOSCAM A/B/E, FATSHARK, RACEBAND) × 8 каналов и 4 уровня мощности
  (25/100/400/800 мВт) — те же данные, что в `vtxtable_example.json`. Полоса 1, канал 1 (5865 МГц)
  выбраны сразу. Поэтому **жёлтой плашки «таблица VTX не настроена» на вкладке «Порты» нет**:
  Configurator показывает её только при доступной и пустой таблице (`usePortsState.js`:
  `vtx_table_available && (bands == 0 || channels == 0 || powerlevels == 0)`).
  Так же ведёт себя `defaults` в CLI и `MSP_RESET_CONF` — сброс возвращает эту же заводскую таблицу,
  а `vtxtable bands 0` (или очистка во вкладке) возвращает пустое состояние, если нужно проверить
  поведение «чистой» прошивки.
* **Таблицу можно перезаписать** во вкладке (число полос/каналов/уровней, затем сетка частот),
  загрузить из файла `vtxtable_example.json` — или вставить строки из `vtxtable_example_cli.txt`
  в «Командную строку» и нажать `save`.
* **Тип передатчика определяется при загрузке** — ровно как `vtxInit()` в прошивке. По умолчанию
  на UART4 стоит функция `TBS_SMARTAUDIO`, поэтому вкладка видит SmartAudio. Если снять функцию
  на вкладке «Порты», передатчик «пропадёт» только после перезагрузки — как на железе.
  В логе эмулятора при старте видно строку `[FC] VTX: TBS SmartAudio (тип 3)`.
* **Таблица живёт во «флеше»** (`vtx_table` и `vtx_pit_mode` в `eeprom.json`): запись во вкладке +
  «Сохранить» → таблица на месте и после «Сохранить и перезагрузить», и после перезапуска эмулятора.
  Кнопка «Сохранить и перезагрузить» внизу вкладки пишет `MSP_SET_*` и `MSP_EEPROM_WRITE` без ребута —
  так же, как настоящий Configurator.
* **CLI**: `vtxtable` печатает таблицу в том же виде, в каком принимает её на вход
  (`vtxtable bands 5`, `vtxtable band 1 BOSCAM_A A FACTORY 5865 …`), поддерживаются подкоманды
  `bands`, `channels`, `powerlevels`, `powervalues`, `powerlabels`, `band`; `vtx_info` печатает
  «level N dBm, power N mW». Ошибки — как в `cliVtxTable()`: `###ERROR IN vtxtable: NOT ENOUGH VALUES (EXPECTED 4)`.

Проверить всё разом:

```
python3 tools/check_vtx_tab.py
```

Скрипт повторяет путь вкладки: читает конфиг и таблицу, заполняет её 5 бандами и 4 уровнями,
делает «Сохранить» → ребут → **перезапуск процесса эмулятора** и сверяет результат (включая CLI).

## Вкладка «ДАТЧИКИ»: поза, живые данные, триммирование и калибровка

Дрон стоит на столе: эмулятор отдаёт неподвижную позу, «живые» показания датчиков
с крошечным шумом (чтобы графики двигались) и нулевое триммирование — как свежая плата.

| Запрос | Код | Что отдаёт |
|---|---|---|
| `MSP_RAW_IMU` | 102 | ровно 18 байт (9 × int16): акселерометр (по Z ровно 1 g = 2048), шум гироскопа ±1 °/с, магнитометр (обнуляется, когда `mag_hardware = NONE`) |
| `MSP_ATTITUDE` | 108 | 6 байт: крен, тангаж (в десятых долях градуса) и **курс в градусах** — без движения, 0.0 / 0.0 / 0° |
| `MSP_ATTITUDE` (поллинг) | 108 | то же статичное значение при каждом опросе (вкладка опрашивает раз в 33 мс) — 3D-модель и приборы неподвижны |
| `MSP_ACC_TRIM` / `MSP_SET_ACC_TRIM` | 240 / 239 | триммирование акселерометра: `pitch, roll` (int16, −300…300) — поля «Триммирование» |
| `MSP_SENSOR_ALIGNMENT` / `MSP_SET_SENSOR_ALIGNMENT` | 126 / 220 | 7 байт: выравнивание гироскопа, акселерометра, магнитометра и `gyro_to_use` |
| `MSP_COMPASS_CONFIG` / `MSP_SET_COMPASS_CONFIG` | 133 / 224 | склонение магнитометра в десятых долях градуса |
| `MSP_SENSOR_CONFIG` / `MSP2_SENSOR_CONFIG_ACTIVE` | 96 / 0x300A | настройки датчиков и «обнаруженные» датчики с идентификаторами, как в `sensor_types.js` (гироскоп 15, акселерометр 16, барометр 4, магнитометр 5, дальномер 2; `0` — датчика на плате нет) |
| `MSP_BOARD_ALIGNMENT`, `MSP_MIXER_CONFIG`, `MSP_STATUS` | 38, 42, 101 | выравнивание платы, тип микшера, состояние (данные для шапки вкладки) |
| `MSP_ACC_CALIBRATION` | 205 | запускает калибровку: через ~1 секунду снимается бит 0 в `MSP_BOARD_INFO.configurationProblems` — вкладка видит, что «акселерометр откалиброван», и убирает предупреждение |
| `MSP_BOARD_INFO` | 4 | `configurationProblems`: бит 0 — «акселерометр не откалиброван» (актуально после `defaults`/сброса), бит 1 — «мотор-протокол выключен» |

Важные детали:

* **Курс — в градусах, а не в десятых долях.** В прошивке `MSP_ATTITUDE` для yaw применяется
  `DECIDEGREES_TO_DEGREES`, и Configurator делит на 10 только крен и тангаж. Если отдать курс
  «как есть» в десятых долях, во вкладке появится «Магнитный курс: 3412.0».
* **Поза не анимируется.** Раньше углы считались по синусу времени: вкладка опрашивает
  `MSP_ATTITUDE` 30 раз в секунду, поэтому фигурка коптера крутилась сама по себе. Теперь ответ
  статичный — дрон лежит на столе, курс 0°.
* **Триммирование живёт в настройках прошивки** (`acc_trim_pitch`, `acc_trim_roll`):
  правка во вкладке → «Сохранить»/«Сохранить и перезагрузить» → значения на месте,
  в том числе после перезапуска эмулятора. В CLI те же значения: `get acc_trim_roll`.
* **Калибровка запоминается во «флеше»** (`acc_calibrated` в `eeprom.json`): после перезапуска
  предупреждение «акселерометр не откалиброван» не возвращается. Команда `defaults` (и сброс
  конфигурации из Configurator) обнуляет калибровку — как `pgResetFn_accelerometerConfig()`.
* **Инструменты вкладки в CLI**: `get acc_trim_pitch`, `get acc_trim_roll`,
  `get gyro_1_sensor_align`, `get align_mag`, `get mag_declination`, `get mag_hardware`.

Проверить всё разом:

```
python3 tools/check_sensors_tab.py
```

## Вкладка «ПИТАНИЕ И БАТАРЕЯ»: батарея, датчики и калибровка

Эмулятор ведёт себя как плата с делителем напряжения и датчиком тока ADC: на столе стоит
4S-батарея с напряжением 16.80 В, моторы стоят, а ток электроники (FC, приёмник, VTX, LED)
показывается живым: ≈0.55 А с небольшим «дыханием» — 0.49…0.61 А. Подробности про живые
цифры и «виртуальный полёт» — в разделе ниже.

| Запрос | Код | Что отдаёт |
|---|---|---|
| `MSP_BATTERY_CONFIG` | 32 | 13 байт: три напряжения (округлённые до 0.1 В), ёмкость, источники датчиков и **точные** напряжения в 0.01 В — 3.30 / 4.30 / 3.50 В, ёмкость 1500 мА·ч |
| `MSP_SET_BATTERY_CONFIG` | 33 | запись всего перечисленного (вкладка шлёт ровно 13 байт) |
| `MSP_VOLTAGE_METER_CONFIG` | 56 | подкадр длиной 5: `id = 10` (метр батареи), тип ADC, масштаб 110, делитель 10, множитель 1 |
| `MSP_SET_VOLTAGE_METER_CONFIG` | 57 | запись калибровки напряжения (кнопка «Калибровать» во вкладке) |
| `MSP_CURRENT_METER_CONFIG` | 40 | два подкадра длиной 6: ADC (`id 10`, масштаб 400) и виртуальный датчик (`id 80`) |
| `MSP_SET_CURRENT_METER_CONFIG` | 41 | запись калибровки тока (масштаб и смещение) |
| `MSP_VOLTAGE_METERS` / `MSP_CURRENT_METERS` | 128 / 129 | живые значения по каждому метру: напряжение в 0.1 В, мА·ч и ток в мА |
| `MSP_BATTERY_STATE` | 130 | 11 байт: банки, ёмкость, напряжение, мА·ч, ток, статус (0 = OK, 3 = «батарея не подключена») и точное напряжение в 0.01 В |
| `MSP_ANALOG` | 110 | то же напряжение для старого пути (статус-бар Configurator) |
| `MSP_SET_MOTOR` | 214 | тест моторов: выход держится до команды «стоп» (1000) — авто-стопа нет, как у `motor_disarmed[]` в прошивке |

Как это выглядит во вкладке:

* **«Батарея»**: «Использовать в качестве датчика напряжения: ADC», «…тока: ADC»,
  минимальное напряжение на банку **3.30**, максимальное **4.30**, предупреждение **3.50**,
  ёмкость **1500** мА·ч. Поля редактируются, список датчиков — как в прошивке
  (`voltageMeterSourceNames` = NONE/ADC/ESC, `currentMeterSourceNames` = NONE/ADC/VIRTUAL/ESC/MSP).
* **«Состояние питания»**: «Подключено: Да (банок: 4)», 16.80 В, 0 мА·ч, 0.00 А, 0.0 Вт.
  Раньше здесь висели «Подключено: Нет», «Израсходовано 893 мА·ч» и «Voltage Drop −16.84 В»:
  эмулятор рисовал расход по времени и не сообщал, сколько банок.
* **Калибровка** появляется при выбранном ADC: можно ввести измеренное напряжение/ток и нажать
  «Калибровать» — новое значение уходит в `MSP_SET_VOLTAGE_METER_CONFIG` / `…CURRENT_METER_CONFIG`
  и попадает в CLI как `vbat_scale` / `ibata_scale`.
* **Датчики «Нет»**: если выбрать `NONE`, вкладка показывает «батарея не подключена» (банок 0,
  0.00 В) — как плата без датчика напряжения, а не выдуманные 16.8 В.
* **Ток под нагрузкой**: включите «виртуальный полёт» (кнопка на мониторе или `sim_flight on`) —
  ток, расход и просадка живут сами, подробности в разделе «Живое питание». Или откройте вкладку
  «Моторы», включите переключатель «Я понимаю риски» и
  подвиньте ползунок — на «Питании» появится ток (четыре ESC: ≈13 А при газе 1500, ≈19 А при 1600,
  ≈49 А на полном) и начнёт тикать «Израсходовано». Моторы держат газ, пока вкладка не пришлёт
  «Стоп» (нули = `mincommand`), — как на железной плате, авто-стопа нет. После «Стоп» ESC выбегают:
  обороты и ток спадают за доли секунды, затем ровный ноль. После перезагрузки счётчик мА·ч
  обнуляется.
* **Сохранение**: правки вкладки уходят в `MSP_SET_*`, затем «Сохранить» пишет «флеш»
  (`MSP_EEPROM_WRITE`) — значения, калибровка и выбранные датчики переживают «Сохранить и
  перезагрузить» и полный перезапуск эмулятора.
* **CLI**: `bat_capacity`, `vbat_min_cell_voltage`, `vbat_max_cell_voltage`,
  `vbat_warning_cell_voltage`, `vbat_full_cell_voltage`, `battery_meter`, `current_meter`,
  `vbat_scale`, `vbat_divider`, `vbat_multiplier`, `ibata_scale`, `ibata_offset`,
  `ibatv_scale`, `ibatv_offset` — имена ровно как в `cli/settings.c` прошивки 4.5.4.

## Живое питание: виртуальный полёт (`sim_flight`) и кнопка на мониторе

Раньше «Состояние питания» на вкладке было мёртвым: пока не тронешь моторы, там всегда
«0.00 А» и «0 мА·ч». Теперь эмулятор ведёт себя как борт, который либо стоит на столе, либо
летает:

| Что | На столе | В «виртуальном полёте» |
|---|---|---|
| Ток | ≈0.55 А, «дышит» 0.49…0.61 А (электроника) | 3…27 А по сценарию газа |
| «Израсходовано mAh» | тикает медленно (≈1.5 мА·ч/с) | ≈15–25 мА·ч/с, видно глазом |
| Напряжение | 16.80 В, медленно падает по мере расхода | проседает под нагрузкой и падает по мере разряда |
| Моторы (`MSP_MOTOR`, вкладка «Моторы») | 1000, обороты 0 | выходы 1200…1900, обороты, температура, ток ESC |

Что за сценарий: взлёт (3 с рампа), висение с подруливанием и «газ в пол» каждые 25 с;
у каждого мотора своя мелочь, поэтому токи ESC не одинаковые. Когда расход доходит до
ёмкости (`bat_capacity`, по умолчанию 1500 мА·ч), борт **садится** (газ убирается за 2.5 с),
затем ставится **новая батарея**: счётчик мА·ч обнуляется, напряжение снова 4.20 В на банку.
Так вкладка проходит весь цикл: OK → «ПРЕДУПРЕЖДЕНИЕ» → посадка → новая батарея.

Время в эмуляторе идёт **в 10 раз быстрее** стенных часов: иначе физика была бы верной, но
цифры менялись бы раз в минуту и вкладка снова казалась бы мёртвой. Масштаб меняется командой
`sim_flight scale <1..600>`.

Как включить и выключить:

| Способ | Как |
|---|---|
| Кнопка на веб-мониторе | карточка **«Питание и батарея»** на <http://127.0.0.1:8088/>: «▶ включить виртуальный полёт», «■ остановить полёт», «сбросить расход» |
| CLI (вкладка CLI Configurator или команда `sim_flight on`) | `sim_flight on` · `sim_flight off` · `sim_flight status` · `sim_flight reset` · `sim_flight scale 10` |

Что при этом видно в CLI:

```
# sim_flight
Virtual flight (emulator)
	state: ON - flight (flying, 12.3 s)
	battery: 4S, 16.31 V (rest 16.42 V), 220 of 1500 mAh, status OK
	current: 8.08 A (electronics 0.55 A + motors)
	drawn: 220 mAh, now about 22.4 mAh per second (time scale x10)
	motors: 1356 1358 1360 1363 (1000 = stopped, gas by scenario when ON)
	'sim_flight on' starts it, 'off' stops, 'reset' clears mAh, 'scale <1..600>' sets the time scale
```

Тонкости:

* Пока идёт полёт, `MSP_SET_MOTOR` (слайдеры вкладки «Моторы») игнорируется — газ держит
  сценарий, как `mixer.c` на взведённом борде. Иначе моторы «дёргались» бы между сценарием и
  ползунком. Остановите полёт — слайдеры снова работают.
* После `save`/`reboot`/`defaults` борт снова «на столе»: полёт — не конфигурация, он не
  сохраняется в «флеш». Счётчик мА·ч тоже обнуляется, как на железной плате.
* Батарея «стоит подключённой» и вне полёта: счётчик тикает и напряжение медленно падает
  (время эмулятора ускорено). Хотите выключить и это — `sim_flight off` и `sim_flight reset`.

Проверить всё разом:

```
python3 tools/check_power_tab.py
```

Скрипт повторяет путь вкладки: читает конфигурацию и живые значения, «крутит» моторы, правит
напряжения, ёмкость, датчики и калибровку, **включает виртуальный полёт** (ток, расход, просадка,
замена разряженной батареи), делает «Сохранить» → «Сохранить и перезагрузить» →
**перезапуск процесса эмулятора** и сверяет результат (включая CLI), а в конце проверяет режим
«батарея не подключена». Всего 47 проверок.

## Адрес веб-монитора: где смотреть страницы эмулятора

Веб-страницы (монитор состояния, виртуальная аппаратура `/tx`, содержимое «флеша» `/msc`)
поднимаются только вместе с ключом `--http` — `run_windows.bat` передаёт `--http 8088` сам,
поэтому адрес по умолчанию — <http://127.0.0.1:8088/>. Если запустить `python -m bfemu` без
ключа, MSP-порт работает, а страниц нет: в логе будет строка
`веб-монитор и /tx выключены … добавьте --http 8088`.

Порт веб-монитора — «человеческий», поэтому занятый порт не роняет эмулятор: он ищет
следующий свободный (8088 → 8089 → …) и печатает настоящий адрес строкой
`порт 8088 занят — веб-монитор поднят на 8089`. Порт MSP, наоборот, строго тот, что указан:
Configurator подключается по конкретному адресу, и «тихо переехать» он не может.

И главное: `127.0.0.1` — это машина, на которой запущен эмулятор. Ссылки вида
`http://127.0.0.1:8090/` в переписке относятся к моей песочнице; у вас открывать нужно тот
адрес, который напечатал ваш запуск.

## Раздел «CLI-команды» на мониторе: команды из CLI Configurator видны сразу

Монитор (`http://127.0.0.1:8088/`) показывает, что происходит с бортом, в том числе две
живые карточки: «Последние MSP-запросы» и **«CLI-команды»**. Раньше вторая оставалась пустой,
если команды вводить в вкладке CLI Configurator: в журнал попадал только путь
`MSP2_CLI_COMMAND` (0x3012), а «сырой» CLI-порт (байт `#` → «Entering CLI Mode») выполнял
команды мимо журнала.

Теперь пишутся **все три пути**:

| Как вводится команда | Что происходит |
|---|---|
| Вкладка **CLI** в Configurator (интерактивный режим, приглашение `# `) | команда и её вывод попадают в карточку «CLI-команды» |
| `MSP.send_cli_command` (неинтерактивный режим, `STX … ETX`) | то же |
| `MSP2_CLI_COMMAND` (0x3012) — так читают настройки новые вкладки | то же |

Обоих карточек касается ещё одно изменение: **они обновляются сами, раз в две секунды**,
без перезагрузки страницы. Ввели команду в Configurator — она появилась в мониторе через
секунду-две; перерисовка происходит только при изменении данных, чтобы не мешать выделять
текст. Журнал хранит последние 40 команд (и 400 строк вывода), так что список не растёт
бесконечно.

## Команды CLI прошивки 4.5.4: больше никаких `UNKNOWN COMMAND`

Раньше вкладка CLI отвечала `###ERROR IN input: UNKNOWN COMMAND, TRY 'HELP'` почти на всё, что
привычно на настоящем борде: не было ни `profile`, ни `rateprofile`, ни `rxfail`, ни `led`.
Теперь распознаются **все команды из `cmdTable[]` прошивки 4.5.4** — 59 имён (плюс четыре
команды самого эмулятора: `blackbox`, `board`, `osd_layout`, `uid`). Вывод сверен построчно
с `src/main/cli/cli.c` (взят тег 4.5.4), состояния живут в тех же таблицах, что видит
Configurator, а тексты ошибок — дословно прошивочные.

* **Профили.** `profile` без аргумента печатает активный профиль PID (`profile 0`), `profile 2`
  переключает, вне 0…3 — `###ERROR IN profile: PROFILE OUTSIDE OF [0..3]`. `rateprofile` —
  то же для рейтов. Это сделано по `cliProfile()`/`cliRateProfile()` 4.5.4.
* **`battery_profile` — команда из МАСТЕРА BF** (в 4.5.4 профилей батареи нет вообще).
  Без аргумента печатает активный (`battery_profile 0`), с индексом 0…2 переключает, вне
  диапазона — `BATTERY PROFILE OUTSIDE OF [0..2]`. Три профиля (пороги ячеек, ёмкость,
  число банок, процент предупреждения, короткое имя), как `pgResetFn_batteryProfiles()`,
  хранятся в `eeprom.json` и меняются битом `0x40` в `MSP_SELECT_SETTING` (мастер-прошивка).
  Подробности — в разделе «Профили батареи» ниже.
* **Ресурсы, таймеры, DMA.** `resource` без аргументов печатает назначенные пины, `resource show` —
  таблицу «пин: владелец», `resource show all` — ещё таймеры и DMA; `resource MOTOR 1 B10`,
  `resource MOTOR 1 NONE` назначают и освобождают пин, занятый пин помечается
  `NOTE: … already assigned to …`. `timer` и `dma` печатают задания платы, `… show` — активные
  таймеры и потоки DMA. Подробности — в разделе «Ресурсы платы, таймеры и DMA» ниже.
* **Настройки приёмника.** `rxfail` печатает все 18 каналов и пишет значение со сеткой 25 мкс
  (`CHANNEL_VALUE_TO_RXFAIL_STEP()` — значение прижимается к 750…2250), `rxrange` — четыре
  диапазона каналов и `reset`, `adjrange` — 30 слотов корректировок.
* **Моторы и микшер.** `motor` (значение 1000…2000, индекс `255` — все моторы), `mmix`
  (ровно 4 коэффициента, `reset`, `load <имя>`), `dshotprog` (команды 1…47, `Command Sent: %d`),
  `dshot_telemetry_info` — таблица ESC.
* **Светодиодная лента.** `led` — 32 строки формата `x,y:направления:функции+наложения:цвет`
  (как `generateLedConfig()`), `color` — 16 цветов HSV, `mode_color` — 48 строк (6 режимов ×
  6 направлений + 11 спец-цветов + AUX-канал ленты).
* **Пищалка.** `beeper`/`beacon` — `Disabled: …`, `list`, `-<имя>`; `play_sound 0` →
  `Playing sound 0: GYRO_CALIBRATED`.
* **Прочее.** `flash_read`/`flash_write`/`flash_erase`/`flash_scan`, `rc_smoothing_info`
  (тип FILTER, `Detected Rx frequency: 33Hz`, три среза с пометкой `(auto)`), `signature`
  (64 hex), `sd_info`, `escprog`, `bind_rx`, `simplified_tuning`.
  `escprog`, `gyroregisters` и `serialpassthrough` работают с оборудованием, которого у
  эмулятора нет: они отвечают ошибкой эмулятора (`NOT SUPPORTED IN THIS EMULATOR`), но уже

## Ресурсы платы, таймеры и DMA (`resource`, `timer`, `dma`)

Команды `resource`/`timer`/`dma` в эмуляторе сделаны один в один по `cliResource()`,
`cliTimer()` и `cliDmaopt()` прошивки 4.5.4 (`src/main/cli/cli.c`): раньше `resource`
отвечал `###ERROR IN resource: INVALID ARGUMENT COUNT` — теперь вывода эмулятора в этих
командах нет вообще, все строки прошивочные.

```
# resource
resource BEEPER 1 C13
resource MOTOR 1 A00
…
# resource show
Currently active IO resource assignments:
(reboot to update)
--------------------
C13: BEEPER
A00: MOTOR 1
…
# resource MOTOR 5 B10             → Resource is set to B10
# resource MOTOR 5 none            → Resource is freed
# resource MOTOR 5 B07             → 
NOTE: B07 already assigned to I2C_SDA 1.

Resource is set to B07
# resource MOTOR 9 A00             → ###ERROR IN resource: INDEX NOT BETWEEN 1 AND 8
# resource NOGA 1 A00              → ###ERROR IN resource: INVALID RESOURCE NAME: 'NOGA'
# resource beeper C13              → Resource is set to C13   (у одиночного ресурса индекс можно не писать)
```

Что важно в деталях (всё сверено с исходниками):

* **Имя ресурса** прошивка сравнивает как `strncasecmp(pch, resourceName, strlen(resourceName))` —
  то есть аргумент обязан начинаться с **полного** имени: `LED` попадает в `LED`, а не в `LED_STRIP`
  (у того имя длиннее), `LED_STRIP` — в `LED_STRIP`. Первое совпадение по таблице побеждает.
* **Индекс** — 1…`RESOURCE_VALUE_MAX_INDEX` (у MOTOR это 8), пропуск индекса у одиночного ресурса
  разрешён: прошивка читает `atoi()` от следующего слова, а `atoi("C13") == 0`, поэтому
  `resource BEEPER C13` — рабочая запись.
* **Занятый пин** не отбирается: `resourceCheck()` печатает `\r\nNOTE: <пин> already assigned to
  <владелец>` (с ведущей пустой строкой), а если пин занят тем же владельцем — освобождает прежний
  слот и дописывает `. <владелец> disabled`. Успех — `\r\nResource is set to <пин>`.
* **Ошибки** — дословно прошивочные: `INVALID RESOURCE NAME: 'X'`, `INDEX NOT BETWEEN 1 AND N`,
  `PARSING FAILED` (пины платы — `A00`…`D15`, как `strToPin()` + таблица IO виртуального борда).
* **Хранение.** Назначенные пины лежат во «флеше» рядом с остальной конфигурацией и переживают
  `save`, `MSP_EEPROM_WRITE` и перезапуск эмулятора; `defaults` возвращает заводскую таблицу.
* **`resource show all`** — это `show` плюс `cliTimer("show")` и `cliDma("show")`:
  «Currently active Timers:» с каналами (`TIM2:` → `    CH1 : MOTOR 1`, свободные — `TIM4: FREE`)
  и «Currently active DMA:» со всеми 16 потоками F405 (`DMA2 Stream 5: SERIAL_RX 1`, свободные — `FREE`).
* **`timer`** печатает по пину две строки — задание и расшифровку канала
  (`timer A00 AF1` и `# pin A00: TIM2 CH1 (AF1)`), `timer sh` (прошивка сверяет строку аргументов
  по её длине) — активные таймеры, `timer A00 list` — `# AF1: TIM2 CH1`, `timer A00 AF1` —
  `# timer A00: no change: AF1`, чужой AF — `INVALID ALTERNATE FUNCTION FOR A00: 'AF7'`,
  у пина без таймера — `timer C13 NONE`.
* **`dma`** печатает таблицу заданий `dmaoptEntryTable` 4.5.4: пары строк на каждое задание
  (`dma UART_TX 1 0` и `# UART_TX 1: DMA2 Stream 7 Channel 4`), свободные слоты скрыты
  (`dma ADC 2` → `dma ADC 2 NONE`), `dma show` — занятые потоки. Устройства — как в прошивке:
  `SPI_SDO/SPI_SDI` и алиасы `SPI_TX/SPI_RX`, `ADC 1…3`, `UART_TX/UART_RX 1…11`
  (`UARTDEV_CONFIG_MAX = 11`), плюс `pin <пин>`. Шина и потоки у платы распаяны жёстко,
  поэтому смена задания отвечает ошибкой эмулятора, а чтение — прошивочное.

**`dump` и `diff` тоже печатают ресурсы** — ровно в том месте, где это делает `printConfig()`
(после имени борта, перед `feature`):

```
# resources
resource MOTOR 5 NONE            ← в дампе видны и свободные слоты: HIDE_UNUSED у `dump` нет
…
# timer
timer A00 AF1
# pin A00: TIM2 CH1 (AF1)
…
# dma
dma SPI_SDO 1 0
# SPI_SDO 1: DMA2 Stream 3 Channel 3
…
dma UART_RX 3 NONE
dma pin A00 NONE
```

В `diff` печатаются только слоты, отличающиеся от заводских (в дампе заводская таблица не
повторяется) — поэтому сохранённый `diff` можно применить на чистой плате.

Как проверить: `python3 tests/smoke_test.py` — раздел 17г, 190 проверок (в том числе 26 про
`resource`/`timer`/`dma` и секции `dump`/`diff`).

## Профили батареи: что это и где искать

Профили батареи — **функция более новых прошивок** (ветка `master`, будущая 4.6). В самой
4.5.4 их нет: в `cli.c` 4.5.4 нет команды `battery_profile`, в MSP — ни кодов, ни полей;
вместо профилей там общие настройки `vbat_min_cell_voltage` и т. п. (они и остаются
источником для вкладки «Питание и батарея»).

Эмулятор умеет профили по мастер-исходникам, чтобы команда «находилась» и работала:

| Где | Что | Источник |
|---|---|---|
| CLI | `battery_profile`, `battery_profile 0…2` | `cliBatteryProfile()` мастера |
| MSP2 | `MSP2_BATTERY_PROFILE` 0x300E (чтение, 13 байт) и `MSP2_SET_BATTERY_PROFILE` 0x300F (запись) | `msp.c` мастера |
| MSP | бит `0x40` в `MSP_SELECT_SETTING` (210) | `BATTERYPROFILE_MASK` = `1 << 6` |
| Имя | `MSP2_GET_TEXT`/`SET_TEXT`, тип 11, до 8 символов | `MSP2TEXT_BATTERY_PROFILE_NAME` |

Профилей **три** (`BATTERY_PROFILE_COUNT`), у каждого — пороги ячеек 330/350/410/430 мВ,
ёмкость, принудительное число банок и процент предупреждения; всё это живёт в `eeprom.json`
и сбрасывается командой `defaults`.

**Почему профиля не видно в окне Configurator.** Configurator 2026.6.2 показывает выбор
профиля батареи на вкладке «Питание и батарея» только при MSP API **≥ 1.48**
(`MSP_STATUS_EX` тогда дописывает `numberOfBatteryProfiles` и активный профиль). Эмулятор
представляется как **4.5.4, API 1.46** — так вкладки живут с теми раскладками, что у 4.5.4.
В CLI и через MSP всё работает уже сейчас; чтобы появился ещё и выбор в окне, нужно поднять
API до 1.48 и дописать поля, которые Configurator с этого момента читает в ~20 местах
(это отдельный раунд работ).

## Страницы эмулятора: кнопки перехода, /aux и /nav

У эмулятора есть страницы для человека. Чтобы не набирать адреса руками, сверху каждой
страницы теперь висит одна и та же полоска кнопок, а для «куда пойти» есть отдельная
страница **`/nav`** (она же `/pages`) — крупные кнопки с пояснением, что где делать:

| Страница | Что там |
|---|---|
| [**`/`**](http://127.0.0.1:8088/) | монитор FC: активные фичи, порты, GPS, моторы, карточка «Режимы», последние MSP-запросы и CLI-команды |
| [**`/tx`**](http://127.0.0.1:8088/tx) | виртуальная аппаратура: стики и тумблеры, «Связать (Bind)», подключить/выдернуть USB-аппаратуру |
| [**`/aux`**](http://127.0.0.1:8088/aux) | режимы: 20 слотов, логика И/ИЛИ, связи, состояние, маска MSP_STATUS и справочник permanentId. **Обновляется раз в секунду** — щёлкайте тумблерами на `/tx` и смотрите, что включилось |
| [**`/msc`**](http://127.0.0.1:8088/msc) | борт в режиме запоминающего устройства: файлы пролётов `LOG0000N.BBL` и `BLACKBOX_ALL.BBL` |
| [**`/nav`**](http://127.0.0.1:8088/nav) | сама страница переходов с кнопками на все четыре |

Страница `/aux` — это «вкладка „Режимы“ в браузере»: она показывает то же, что Configurator
(и читает те же `MSP_MODE_RANGES` 34 / `MSP_MODE_RANGES_EXTRA` 238), но рядом с тумблерами:
удобно проверять связки «режим включается вместе с режимом» и правила `aux` из CLI, не
переключаясь между окнами. Таблица рисуется ещё на сервере, поэтому она не пустая даже до
первого запроса страницы, а дальше обновляется по `/api/state`.

Кнопки-полоска одинаковая на всех страницах (`Монитор · Аппаратура (TX) · Режимы (AUX) ·
Чёрный ящик (MSC) · Переходы`), текущая подсвечена, поэтому «вернуться назад» кнопкой браузера
пользоваться не обязательно.

## Вкладка «РЕЖИМЫ»: диапазоны AUX, живое состояние и CLI как в прошивке

Раньше вкладка открывалась пустой и «не хотела» работать: на `MSP_MODE_RANGES` (34) эмулятор
отвечал одной записью длиной пять байт, а `MSP_MODE_RANGES_EXTRA` (238) не обрабатывался вовсе —
Configurator разбирал такой ответ как «слотов нет». При этом CLI показывал строку
`aux 0 0 0 900 900` — и это выглядело как противоречие. Теперь эмулятор держит ровно тот же
массив из 20 слотов, что и прошивка, и оба пути показывают одно и то же.

| Запрос | Код | Что отдаёт |
|---|---|---|
| `MSP_MODE_RANGES` | 34 | **все 20 слотов** по 4 байта: permanentId режима, номер AUX, startStep, endStep. Пустой слот — «0 0 0 0» (режим ARM, 900/900) |
| `MSP_MODE_RANGES_EXTRA` | 238 | счётчик 20 и по 3 байта на слот: permanentId, логика (`0` = ИЛИ, `1` = И), linkedTo |
| `MSP_SET_MODE_RANGE` | 35 | запись слота: index, permanentId, AUX, startStep, endStep и — если байты остались — логика и linkedTo. Вкладка шлёт семь байт, CLI-совместимый путь принимает и пять |
| `MSP_BOXNAMES` / `MSP_BOXIDS` | 116 / 119 | список режимов (13 штук) и их permanent id — вкладка строит строки по этому порядку |
| `MSP_STATUS` | 101 | `CONFIG.mode` — маска включённых режимов: по ней вкладка рисует точку «включён» |

Как это выглядит во вкладке:

* **Свежий борт пустой — это правильно.** Все 20 слотов хранят «ARM, 900/900», а Configurator
  считает такие записи заполнителями и строк не рисует. Так же ведёт себя настоящая плата
  после `defaults`; CLI при этом честно печатает все 20 строк, включая пустые.
* **«Добавить диапазон»** → слайдеры (шаг 25 мкс, 900…2100) → `MSP_SET_MODE_RANGE`: строка
  появляется сразу, а CLI тут же показывает `aux 0 0 0 1300 1700 0 0`.
* **Логика И/ИЛИ и «Добавить связь»** живут в `MSP_MODE_RANGES_EXTRA` и видны в CLI как
  шестое и седьмое число строки.
* **Состояние живое**: режим включён, когда канал AUX попадает в диапазон
  (`900 + 25 * step` — как `isRangeActive()` в `rc_modes.c`). Точки на вкладке горят по
  `MSP_STATUS`, поэтому тумблеры на странице аппаратуры (`/tx`) и в `tools/tx.py` двигают
  ровно то, что видно в Configurator. Логика И/ИЛИ и связи считаются по `updateActivatedModes()`.
* **Правки из CLI видны вкладке и наоборот** — состояние одно: `aux 5 1 4 1500 2000`
  добавляет строку AUX5, а удаление диапазона на вкладке возвращает слот к «900/900».
* **CLI как в прошивке**: `aux` печатает 20 строк формата
  `aux index permId aux MIN MAX logic linkedTo` (`printAux` из `cli.c`), `diff` — только
  настроенные.
* **Список режимов — как на железной плате**: `MSP_BOXNAMES`/`MSP_BOXIDS` собираются по
  правилам `initActiveBoxIds()` (`msp_box.c`): ARM и PREARM всегда, остальное — по фичам,
  датчикам, микшеру и протоколу моторов. На этой сборке выходит **28 режимов** — есть BEEPER,
  TELEMETRY, OSD DISABLE, BLACKBOX, VTX PIT MODE, READY и другие; выключенные режимы
  (MAG, LEDLOW, AIR MODE, CALIB) в списке не появляются, поэтому и вкладка их не показывает.
  Ответ длиннее 255 байт уходит «джамбо»-кадром MSP v1 — так же, как на прошивке.
* **«Сохранить и перезагрузить»**: слоты, логика и связи пишутся во «флеш» и переживают
  перезапуск; `defaults` возвращает все 20 слотов к пустым.

Одна оговорка: маска режимов в `MSP_STATUS` у нас собрана по позициям режимов в списке
`MSP_BOXNAMES` — именно так её читает Configurator 2026.6.2 (`bit_check(config.mode, mode.index)`),
поэтому подсветка совпадает с тумблерами. Это ровно то, что делает прошивка:
`packFlightModeFlags()` нумерует биты по порядку *активных* режимов и не ставит бит для
режима, которого нет в списке.

### Почему `aux 1 11 1 1300 1700` «не прописывается», и что в этом случае делает плата

Второе число в строке `aux` — не порядковый номер режима, а его **permanentId**: постоянный
номер, который прошивка навсегда закрепила за смыслом режима («ARM» — 0, «ANGLE» — 1,
«HORIZON» — 2, …). Номера **не сквозные**: часть значений зарезервирована под удалённые
режимы и использовать их нельзя.

| Что видно в CLI | Что происходит |
|---|---|
| `aux 1 11 1 1300 1700` | permanentId 11 — это удалённый «GPS HOLD», такого режима в 4.5.4 нет. Разобрано всего 3 значения (режим не считается, канал и два конца диапазона — считаются) → `validArgumentCount != 4/5/6` → слот обнуляется целиком (`memset`). В ответ CLI печатает уже пустой слот: `aux 1 0 0 900 900 0 0` |
| `aux 1 11 1 1300 1700 0 0` | шесть чисел: канал, диапазон и логика записались, а режим остался прежним (после обнуления это ARM, в строке ответа видно `aux 1 0 1 1300 1700 0 0`). Так же ведёт себя железная плата — и это повод перепроверить номер режима, а не игнорировать строку |
| `aux 1 1 1 1300 1700 0 0` | верный номер (ANGLE = 1) — строка появляется и в CLI, и на вкладке |
| 4 или 5 чисел | 4 → логика сбрасывается в «ИЛИ», связь снимается; 5 → снимается только связь. Это «обратная совместимость» из `cliAux`, старые строки без `logic linkedTo` тоже работают |

**Удалённые номера, которых в 4.5.4 нет:** 3 (BARO), 9 (CAMTRIG), 10 (GPS HOME), 11 (GPS HOLD),
14 (LEDMAX), 16 (LLIGHTS), 18 (GOVERNOR), 21 (GTUNE), 22 (RANGEFINDER), 38 (3D ON A SWITCH).
В исходниках они оставлены комментариями — именно чтобы номера не переиспользовали.

**Режимы этой платы и их permanentId** (тот же список — в карточке «Режимы» монитора
эмулятора и в `MSP_BOXIDS`):

| permanentId | 0 | 1 | 2 | 6 | 7 | 13 | 19 | 20 | 26 | 27 | 30 | 31 | 32 | 33 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| режим | ARM | ANGLE | HORIZON | HEADFREE | HEADADJ | BEEPER | OSD DISABLE | TELEMETRY | BLACKBOX | FAILSAFE | FPV ANGLE MIX | BLACKBOX ERASE | CAMERA CONTROL 1 | CAMERA CONTROL 2 |

| permanentId | 34 | 35 | 36 | 37 | 39 | 45 | 46 | 47 | 48 | 49 | 51 | 52 | 53 | 54 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| режим | CAMERA CONTROL 3 | FLIP OVER AFTER CRASH | PREARM | GPS BEEP SATELLITE COUNT | VTX PIT MODE | PARALYZE | GPS RESCUE | ACRO TRAINER | VTX CONTROL DISABLE | LAUNCH CONTROL | STICK COMMANDS DISABLE | BEEPER MUTE | READY | LAP TIMER RESET |

Ещё два правила, которые видно на вкладке:

* режим, которого нет в `MSP_BOXNAMES` (например LEDLOW при выключенной фиче LED_STRIP),
  можно записать в слот из CLI — строка будет в `aux`, но вкладка её не покажет и точка
  состояния не загорится: вкладка перебирает только список режимов платы;
* диапазон вне сетки округляется вниз к шагу 25 мкс: `1310 1707` → `1300 1700`
  (`CHANNEL_VALUE_TO_STEP()`), а если `start >= end`, строка на вкладке считается
  заполнителем и не рисуется.

Проверить всё разом:

```
python3 tools/check_modes_tab.py
```

Скрипт повторяет путь вкладки (загрузка, «Добавить диапазон», связь, логика, живое состояние,
CLI, «Сохранить и перезагрузить», `defaults`, список режимов и правила permanentId,
монитор и страницы `/nav` с `/aux`, команды CLI прошивки) — 73 проверки.

## Вкладка «МОТОРЫ»: слайдеры реально крутят моторы, телеметрия живая

Раньше вкладка была «мёртвой»: выходы менялись, но ни оборотов, ни тока, ни температуры не было —
в мониторе эмулятора вкладка выглядела рабочей, а в Configurator ничего не происходило. Теперь
эмулятор ведёт модель ESC: команды слайдеров и мастера (`MSP_SET_MOTOR`, 214) реально меняют
выходы, а по ним считаются обороты, ток, нагрев и просадка питания.

| Запрос | Код | Что отдаёт |
|---|---|---|
| `MSP_MOTOR` | 104 | **восемь** `u16` — текущие выходы (как `msp.c` 4.5.4). В покое 1000 (`motor_disarmed[]` в нуле), у несуществующих моторов — нули. Вкладка поллит его каждые 50 мс |
| `MSP_MOTOR_TELEMETRY` | 139 | 4 мотора × 13 байт: обороты (об/мин), доля битых кадров, температура ESC, напряжение, ток, расход. Нужна включённая DShot-телеметрия (`dshot_bidir`) |
| `MSP_MOTOR_3D_CONFIG` | 124 | 6 байт: 1406 / 1514 (мёртвые зоны 3D) и 1460 (нейтраль) |
| `MSP_SET_MOTOR_3D_CONFIG` | 217 | запись этих трёх значений (вкладка шлёт их при «Сохранить») |
| `MSP2_MOTOR_OUTPUT_REORDERING` | 0x3001 | 9 байт: число моторов и порядок выходов (0…7), как `pgResetFn_motorConfig` |
| `MSP2_SET_MOTOR_OUTPUT_REORDERING` | 0x3002 | запись порядка выходов |
| `MSP2_SEND_DSHOT_COMMAND` | 0x3003 | команда ESC-контроллеру (13 = включить расширенную телеметрию); эмулятор её принимает и пишет в лог |
| `MSP_SET_ARMING_DISABLED` | 99 | запрет взвода `ARMING_DISABLED_MSP` — вкладка поднимает его на время теста, чтобы борт нельзя было взвести |

Как это выглядит во вкладке:

* Ползунок мастера или отдельный слайдер → `MSP_SET_MOTOR` → моторы крутятся; обороты, ток и
  температура ESC растут **постепенно** (модель интегрируется подшагами по 5 мс, поэтому поллинг
  каждые 50 мс видит плавную раскрутку, а не мгновенный скачок).
* Ориентиры (4S, винты 2207, полюсов 14): 1500 мкс → 12 000 об/мин, ≈13 А суммарно; 1600 → 14 400,
  ≈19 А; 2000 (полный газ) → 24 000, ≈49 А, нагрев ESC до ≈69 °C.
* Напряжение под током проседает: 16.80 → 16.61 В при газе 1600 и 16.31 В на полном. Ту же цифру
  показывают вкладка «Питание и батарея», OSD и статус-бар — источник один.
* «Стоп» (вкладка шлёт нули) → выходы возвращаются к 1000, ESC **выбегают**: через 0.35 с ещё
  ≈2 800 об/мин и ≈0.5 А на мотор, через 1.5 с — ровный ноль. Авто-стопа по таймауту нет — так же
  ведёт себя прошивка (`motor_disarmed[]` держится, пока не придёт новая команда).
* «Сохранить и перезагрузить»: правки вкладки (газ, полюса, протокол, idle, 3D-зоны, порядок
  выходов) уходят во «флеш» и переживают перезапуск эмулятора, а тест моторов после ребута
  прекращается — борт не «убегает».

Проверить всё разом:

```
python3 tools/check_motors_tab.py
```

Скрипт загружает вкладку теми же кадрами, что шлёт Configurator, включает «Я понимаю риски»,
крутит моторы слайдерами, читает живую телеметрию, проверяет выбег после «Стоп», правит и
сохраняет настройки с перезапуском и сверяет монитор (`/api/state`).

## Вкладка «FAILSAFE»: диапазон импульсов, «Этап 1» и «Этап 2»

Эмулятор отдаёт заводские значения прошивки 4.5.4 — то же самое, что показывает свежая плата.

| Запрос | Код | Что отдаёт |
|---|---|---|
| `MSP_RX_CONFIG` / `…SET_RX_CONFIG` | 44 / 45 | 38 байт, в том числе «Настройка допустимого диапазона длительности импульсов»: `rx_min_usec` 885, `rx_max_usec` 2115 |
| `MSP_FAILSAFE_CONFIG` / `…SET_FAILSAFE_CONFIG` | 75 / 76 | 8 байт: задержка 15 (1.5 с), время посадки 10 (1.0 с), газ 1000, тумблер «Этап 1» (0), лимит низкого газа 100 (10 с), процедура DROP (1) |
| `MSP_RXFAIL_CONFIG` / `…SET_RXFAIL_CONFIG` | 77 / 78 | по 3 байта на каждый из 16 каналов: режим и значение |
| `MSP_RC` | 105 | 16 каналов — столько отдаёт серийный приёмник CRSF |
| `MSP_RX_MAP` | 64 | 8 байт — заводская карта AETR1234 → `[0, 1, 3, 2, 4, 5, 6, 7]` |
| `MSP_RSSI_CONFIG`, `MSP_FEATURE_CONFIG`, `MSP_BOXNAMES`, `MSP_BOXIDS`, `MSP_MODE_RANGES` | 50, 37, 116, 119, 125 | RSSI-канал, фичи, список режимов для подписей AUX-каналов |
| `MSP_GPS_RESCUE` / `…SET_GPS_RESCUE` | 135 / 225 | 26 байт настроек спасения по GPS (видны, если выбрать процедуру «GPS Rescue») |

Важные детали:

* **«Этап 1» — 16 строк, как на реальной плате.** `MSP_RXFAIL_CONFIG` отдаёт по 3 байта
  на каждый канал приёмника; раньше он отдавал 18 байт подряд, из которых вкладка собирала
  6 «каналов» с мусорными значениями.
* **Стики — «Автоматически», AUX — «Удержание».** Так задаёт `pgResetFn_rxFailsafeChannelConfigs()`
  в `rx.c`: каналы 0–3 получают `RX_FAILSAFE_MODE_AUTO` (у газа значение `RX_MIN_USEC` = 885 мкс
  на сетке 25 мкс, то есть 875), AUX — `RX_FAILSAFE_MODE_HOLD` со средним 1500.
* **Задержка «Этапа 2» — 1.5 с, а не 1.0.** `failsafe_delay` в прошивке равен 15 (в десятых долях
  секунды), `failsafe_off_delay` — 10 (1.0 с). Раньше в базе эмулятора были старые значения
  (10 и 200), и вкладка показывала 1.0 с / 20 с.
* **Значения «Этапа 1» округляются до сетки 25 мкс** — так же, как прошивка переводит
  `CHANNEL_VALUE_TO_RXFAIL_STEP()` и обратно: введёте 1487 — прочитаете 1475.
* **Всё сохраняется**: `MSP_SET_FAILSAFE_CONFIG`, `MSP_SET_RXFAIL_CONFIG`, `MSP_SET_RX_CONFIG`
  пишут в те же настройки, что видны в CLI, а «Сохранить и перезагрузить» кладёт их во «флеш».
  «Этап 1» (как `PG_RX_FAILSAFE_CHANNEL_CONFIG` в прошивке) тоже живёт во «флеше» и
  переживает перезапуск; команда `defaults` возвращает заводские значения.
* **CLI**: `rx_min_usec`, `rx_max_usec`, `failsafe_delay`, `failsafe_off_delay`, `failsafe_throttle`,
  `failsafe_switch_mode`, `failsafe_throttle_low_delay`, `failsafe_procedure`,

## Демонстрация failsafe: страница `/failsafe`, кнопка на мониторе и CLI `sim_failsafe`

Для занятий со студентами эмулятор умеет **показывать работу failsafe целиком** — не только
таблицу параметров вкладки, а саму машину фаз прошивки 4.5.4: потерю сигнала, «Этап 1»,
**точку отката**, «Этап 2» (посадка / падение / GPS-спасение) и возврат управления.

**Где запустить.** На мониторе (`/`) есть карточка «Failsafe — демонстрация» с кнопкой
«Открыть демонстрацию» → страница `/failsafe` (адрес тот же, что у монитора, например
`http://127.0.0.1:8088/failsafe`). В CLI (консоль Configurator, сервер эмулятора) работает
команда `sim_failsafe`.

**Что делает демонстрация.** Демо стартует «в воздухе»: борт взведён, газ висения 1500 мкс
(иначе сработал бы JustDisarm, как на столе). Дальше действуют только прошивочные правила
(`failsafe.c`, `rx.c`, `rc_controls.c`, `gps_rescue.c`; копии исходников — в
`docs/bf454-failsafe/`):

| Шаг | Что происходит | Откуда правило |
|---|---|---|
| «Потерять сигнал» | кадры держат последние значения 300 мс | `rx.c: MAX_INVALID_PULSE_TIME_MS` |
| «Этап 1» | каналы по таблице «Этап 1»: стики — в центр, газ — `rx_min_usec`; идёт страж-время `failsafe_delay` (1.5 с) | `rx.c`, rxfail |
| **ТОЧКА ОТКАТА** | метка на таймлайне и плашка: пока идёт страж-время — «откат возможен: сигнал вернёт управление, осталось N с», после — «откат невозможен: Этап 2 идёт» | `failsafe.c: FAILSAFE_RX_LOSS_DETECTED` |
| «Этап 2» | `AUTO-LAND` — газ убирается за `failsafe_off_delay` (1 с), затем моторы в 0; `DROP` — моторы сразу; `GPS-RESCUE` — спасение по `gps_rescue.c` | `failsafe.c`, `gps_rescue.c` |
| моторы в 0, взвод запрещён | снятие с взвода, `ARMING_DISABLED_FAILSAFE`, бипер `RX_LOST` | `failsafe.c: FAILSAFE_LANDED` |
| «Вернуть сигнал» | ждём `failsafe_recovery_delay` (0.5 с) валидных данных → IDLE, взвод разрешён | `failsafeIsReceivingRxData()` |

**Точка отката** — центральное место страницы: метка на таймлайне, плашка
«откат возможен / невозможен» и кнопка «Вернуть сигнал» рядом: видно, что до входа в «Этап 2»
пилот ещё возвращает управление, а после — уже нет.

**Тумблер FAILSAFE** (вкладка «Режимы») проверяется с той же страницы: `STAGE1` — тумблер «как
потеря сигнала» (страж-время, выход сразу после снятия — preset 0), `KILL` — моторы гаснут
немедленно, `STAGE2` — «Этап 2» без страж-времени.

**JustDisarm**: если газ был ниже `min_check` дольше `failsafe_throttle_low_delay` (10 с),
борт на земле выключается без процедуры — на странице есть кнопка «Стоять на земле (взведён)».

**GPS-спасение**: панель показывает фазы `INITIALIZE → ATTAIN_ALT → ROTATE → FLY_HOME →
DESCENT → LANDING → COMPLETE`, высоту и расстояние до дома, газ, а таблица из 16 параметров —
`gps_rescue_*` и «что делает сейчас». Сценарии ошибок: «мало спутников» → `RESCUE_LOWSATS`
(при `sanity checks = FS_ONLY` и потерянной связи — `ABORT`, моторы в 0) и «газа зависания
не хватает» → 10 с без набора высоты → посадка на месте (`RESCUE_LANDING`).

**Масштаб времени** ×1 / ×0.5 / ×0.25 (по умолчанию ×0.25): прошивочные времена не меняются —
растягивается только показ, часы демо идут по-настоящему и просто медленнее. ×1 — честные
тайминги.

**CLI:**

```

sim_failsafe loss|restore|reset    потерять сигнал / вернуть / сбросить демо
sim_failsafe arm|disarm            «в воздухе» (газ 1500) / выключить моторы
sim_failsafe box on|off            щёлкнуть тумблером FAILSAFE (вкладка «Режимы»)
sim_failsafe switch 0|1|2          режим тумблера: STAGE1 / KILL / STAGE2
sim_failsafe scenario none|low_sats|hover_low    сценарий проверок спасения
sim_failsafe procedure auto-land|drop|gps-rescue процедура «Этапа 2»
sim_failsafe scale 1|0.5|0.25      скорость показа
sim_failsafe status                состояние, таймлайн, точка отката, каналы, журнал
```

## Вкладка «СЕРВОПРИВОДЫ»: build-опции прошивки и сервоприводы

### Почему вкладки не было

Configurator 2026.6.2 показывает вкладку «Сервоприводы» не всем платам. Решение принимается
в трёх местах, и **во всех трёх нужны build-опции прошивки**:

| Где | Что смотрит |
|---|---|
| `MSPHelper.js`, разбор `MSP_BUILD_INFO` | при MSP API >= 1.46 читает список `u16`-кодов **до нулевого кода** и складывает в `FC.CONFIG.buildOptions` |
| `serial_backend.js`, `finishOpen()` | если `buildOptions` пуст → добавляет все вкладки; иначе — только те, для которых в списке есть нужная опция (`servos` ← `USE_SERVOS` или `USE_WING`) |
| `sidebar_items.js` / `Features.js` | пункт меню «Сервоприводы» требует `USE_SERVOS`/`USE_WING`; функция `SERVO_TILT` во вкладке «Конфигурация» — `dependsOn: SERVOS` |

Раньше эмулятор отдавал `MSP_BUILD_INFO` без списка опций: `SERVO_TILT` во вкладке
«Конфигурация» включался (он хранится в битах фич), а сам пункт меню «Сервоприводы» пропадал —
`GUI.allowedTabs` его не разрешал. Теперь список отдаётся.

### MSP_BUILD_INFO: 46 байт

|---|---|---|
| 0 | 11 | дата сборки, `Sep 24 2026` (ровно 11 байт, **без** лишнего пробела) |
| 11 | 8 | время сборки, `12:00:00` |

| 26 | 9 × 2 | build-опции, `u16` каждая |

### Что вкладка читает и пишет

`ServosTab.vue` в 2026.6.2 работает так:

| Шаг | Запрос | Код | Длина | Содержимое |
|---|---|---|---|---|
| Загрузка | `MSP_SERVO_CONFIGURATIONS` | 120 | 8 × 12 = 96 байт | на сервопривод: `min` (u16), `max` (u16), `middle` (u16), `rate` (u8), `forwardFromChannel` (u8), `reversedSources` (u32) |
| Загрузка | `MSP_SERVO_MIX_RULES` | 241 | 16 × 7 = 112 байт | правило микшера |
| Загрузка | `MSP_RC` | 105 | 32 байта | 16 каналов — из них вкладка берёт выбор «перенаправление с канала» |
| Загрузка | `MSP_BOXNAMES` | 116 | строка | список режимов для поля «box» |
| Живые значения | `MSP_SERVO` | 103 | 8 × 2 = 16 байт | текущие импульсы сервоприводов |
| Сохранение | `MSP_SET_SERVO_CONFIGURATION` | 212 | 13 байт на сервопривод | `index` + те же 12 байт |
| Сохранение | `MSP_EEPROM_WRITE` | 250 | — | «Сохранить» |

Заводские значения — как в `pgResetFn_servoParams()` прошивки 4.5.4: `min` 1000, `middle` 1500,
`max` 2000, `rate` 100, `forwardFromChannel` = `CHANNEL_FORWARDING_DISABLED` (0xFF, «не
перенаправлять»), правила микшера — нули.

Две тонкости формата, на которых вкладка ломается:

* длина ответа 120 **обязана быть кратна 12** — иначе `MSPHelper.js` не создаёт ни одной записи,
  `FC.SERVO_CONFIG.length === 0` и вкладка показывает «не поддерживается» даже при наличии опции;
* `MSP.promise` ждёт **полный ответ** на каждый `MSP_SET_SERVO_CONFIGURATION`, поэтому на 212
  эмулятор отвечает пустым ACK (иначе «Сохранить» зависает), а индекс >= 8 отклоняет, как
  `msp.c`.

`MSP_SERVO` (103) отдаёт не «середину», а значение RC-канала, если у сервопривода задано
перенаправление: например, после записи `servo 2 = 900/2100/1500, rate 50, forward 4` (AUX 1)
восьмое значение становилось 900 мкс — на столе AUX 1 стоит в 900.

## Вкладка «ПРИЁМНИК»: каналы, «Предпросмотр» и карта каналов

Вкладка загружала данные, но коптер в окне «Предпросмотр» постоянно вращался на месте.
Причина была не во вкладке, а в ответе `MSP_RC` (105): эмулятор отдавал каналы в порядке
`Крен, Тангаж, Газ, Рыск`, то есть **Рыск стоял на 1000 мкс, а Газ — на 1500**.

Прошивка хранит `rcData[]` в порядке `rcChannelLetters = "AERT…"` (`src/main/rx/rx.c`), то есть
индекс 2 — это рыск, индекс 3 — газ. Configurator подписывает первые четыре полосы вкладки жёстко
(Крен/Тангаж/Рыск/Газ) и вращает модель предпросмотра по каналам 0…2 через
`RateCurve.rcCommandRawToDegreesPerSecond()`. Рыск 1000 мкс при ACTUAL-рейтах (rc_rate 7000)
даёт −1998 °/с — полный разворот за 0,18 с. Теперь на столе отдаётся
`1500, 1500, 1500, 1000` — модель стоит, полосы живые (у AUX 1 микрошум ±2 мкс).

Стики специально отдаются **без** шума: даже ±2 мкс при таких рейтах — это ~30 °/с, и модель
медленно уезжала бы.

### Что читает и пишет вкладка

| MSP | Байт | Что внутри |
|---|---|---|
| `MSP_FEATURE_CONFIG` (36) | 4 | режим приёмника (RX_SERIAL/TELEMETRY) и «Аналоговый RSSI-вход» (RSSI_ADC) |
| `MSP_RC` (105) | 32 | 16 каналов в порядке A/E/R/T — стики 1500, газ 1000, AUX 1000 |
| `MSP_RSSI_CONFIG` (50) | 1 | канал RSSI (0 = выключен); запись — `MSP_SET_RSSI_CONFIG` (51) в `rssi_channel` |
| `MSP_RC_TUNING` (111) | 23 | рейты ACTUAL: 7/67/0, лимиты 1998 °/с (в GUI 70/670/0.00) |
| `MSP_RX_MAP` (64) | 8 | карта каналов AETR1234 → `[0,1,3,2,4,5,6,7]`; запись — `65` |
| `MSP_RC_DEADBAND` (125) | 5 | RC 0 / Yaw 0 / 3D-газ 50 мкс; запись — `218` |
| `MSP_RX_CONFIG` (44) | 38 | CRSF (9), «Диапазон стиков» 1050/1500/2000, импульсы 885…2115, Airmode 30 %, RC-сглаживание ON/30/Авто |
| `MSP_MIXER_CONFIG` (42) | 2 | микшер QUADX (2) |

Сохранение повторяет `saveConfig()` вкладки: `65` → `51` → `218` → `45` → `MSP_EEPROM_WRITE`
(+ `MSP_SET_FEATURE_CONFIG` при «Сохранить и перезагрузить»). Все четыре кода разбираются по
смыслу и пишут в те же CLI-настройки, что видны командой `get` — вкладка и CLI совпадают,
правки переживают перезапуск эмулятора, а `defaults` возвращает `AETR1234` и выключенный RSSI.

### Как проверить вкладку разом

```
python3 tools/check_receiver_tab.py
```

Скрипт повторяет загрузку вкладки, считает угловые скорости предпросмотра той же формулой, что
`RateCurve.js` (0 °/с — модель стоит; с прежними данными было бы 1998 °/с), меняет карту каналов,
RSSI, дедбенды и диапазон стиков, делает «Сохранить и перезагрузить», перезапускает процесс
эмулятора, сверяет значения через CLI (`get`, `map`, `dump`) и проверяет `defaults`.

## Виртуальная аппаратура (TX): «пульт» и подключение по USB

Настоящей аппаратуры у стенда нет, поэтому эмулятор сам отдаёт каналы `MSP_RC`: у него есть
состояние 16 каналов (стики в центре, газ внизу, тумблеры AUX выключены), которое можно менять
на лету. Configurator опрашивает `MSP_RC` каждые 33 мс, поэтому вкладка «Приёмник» сразу
показывает движения, «Предпросмотр» наклоняет и вращает коптер, а вкладка «Режимы» —
включает режимы от AUX.

### Подключение и отключение аппаратуры (кто управляет каналами)

На странице <http://127.0.0.1:8088/tx> три роли, как у настоящего стенда:

| Кнопка | Что происходит |
|---|---|
| **Подключить аппаратуру** | Управление переходит к **настоящей** аппаратуре (пульт по USB или приёмник в COM-порту). Ползунки, тумблеры и крутилки на странице **отключаются** (карточки гаснут). Связи пока нет: запустите `run_tx_joystick.bat` / `run_tx_wire.bat` и нажмите «Связать (Bind)» |
| **Отключить (выдернуть USB)** | Настоящая аппаратура отсоединена: управление **возвращается этой странице**, ползунки снова активны. Связи нет — нужен бинд |
| **Связать (Bind)** | Создаёт связь с виртуальным контроллером — **только после этого каналы активируются** (2 секунды поиска, как на приёмнике). `python tools\tx.py bind` / `unbind` — то же из консоли |

Пока связи нет, `MSP_RC` отдаёт значения «Этапа 1» из вкладки Failsafe (`rx.c`: стики — `midrc`,
газ — `rx_min_usec`, каналы HOLD держат последнее), а в `MSP_STATUS_EX` поднят флаг
`ARMING_DISABLED_RX_FAILSAFE` (1 << 2) — Configurator показывает предупреждение и подсвечивает
полосы жёлтым.

Кто именно управляет, видно в `/api/rc`: `control.mode` = `virtual` (страница) или `physical`
(настоящая аппаратура), `control.text` — человеческое описание. Из консоли то же самое:
`python tools\tx.py control virtual|physical`. Запуск `tools/tx.py joystick` или `wire` сам
забирает управление, а при Ctrl+C возвращает его странице.

**У каналов всегда один хозяин — и в обе стороны.** Пока управление у страницы (обычное
состояние), данные пульта и приёмника **отклоняются**: эмулятор отвечает HTTP 409, а инструмент
пишет «управление каналами сейчас у страницы /tx» и ждёт. Пока нажато «Подключить аппаратуру» и
каналами владеет пульт, молчат уже страница и скрипты — их запись тоже отклоняется (409). Иначе
пульт и ползунки писали бы каналы одновременно — это и выглядело как «срывы».

Состояние «в эфире / нет связи» и бинд — не конфигурация FC: во «флеш» они не пишутся; после
перезапуска эмулятора аппаратура снова «подключена и связана», стики в центре.

### Калибровка AUX: тумблеры и крутилки

Стики калибруются `--detect` (четыре шага), а тумблеры и крутилки — отдельно: `--detect-aux`
(или автоматически следом за стиками, если запустить `--detect`). Как это работает:

1. Инструмент показывает, какие свободные оси в покое стоят на упоре — это кандидаты в тумблеры
   (или «мёртвые» оси, которые пульт не отдаёт).
2. Вы переводите тумблер во все положения (трёхпозиционный — через все три), крутилку крутите
   до упоров. Нажимать ничего не надо: движение ловится само.
3. По характеру движения определяется тип:

| Что видно на оси | Тип | Канал |
|---|---|---|
| две устойчивые позиции | тумблер на 2 положения | 1000 / 2000 |
| три устойчивые позиции | тумблер на 3 положения | 1000 / 1500 / 2000 |
| плавно, без устойчивых «кучек» | крутилка | 1000…2000 линейно (ход — по упорам) |

4. Каналы выдаются **по порядку обнаружения**: первый тумблер → AUX1 (на пульте это обычно CH5),
   второй → AUX2 (CH6) и так далее; вручную — `--aux-map 3=switch2:3`. Раскладка сохраняется
   в `tx_map.json` рядом со стиками и подхватывается при следующем запуске.
5. Раскладка печатается при запуске и уходит на страницу `/tx`: в «Состоянии» есть строка
   `AUX-каналы: AUX1 ← тумблер (2 положения) — ось 3, …`.

Если ось за всю калибровку ни разу не шевельнулась, инструмент прямо говорит, что делать: в режиме
USB Joystick пульт отдаёт по USB только каналы, назначенные в микшере модели (`MODEL SETUP → MIXES`),
поэтому тумблер надо сначала повесить на канал (обычно `CH5`, `CH6`), а потом калибровать заново.
Проверить руками: `python tools\tx.py axes` — щёлкать тумблерами и смотреть, какая ось меняется.

### Один инструмент за раз: почему каналы «прыгают» и рыск уезжает в AUX

Каналы должен вести ровно один инструмент. Если оставить открытым прежнее окно
`run_tx_joystick.bat` (или `python tools\tx.py joystick`) и запустить второе, оба будут писать
каналы со своими раскладками осей — снаружи это выглядит как **«рыск уводит AUX 2»**, «полосы
прыгают», «коптер в Предпросмотре постоянно крутится». Именно так выглядит симптом, который
не воспроизводится на чистом эмуляторе: сам маппинг верен, но его перезаписывает старое окно.

Что теперь делает поставка:

* новое окно при старте смотрит `tx_lock.json` и **останавливается** с подсказкой, если каналы уже
  ведёт другой запуск (`PID …`); обойти можно ключом `--force`, а Ctrl+C в прежнем окне снимает замок.
  Если прежний запуск сделан **старой** сборкой (замка ещё не было), инструмент не остановится, но при
  старте проверит, кто писал каналы последним, и скажет: «каналы только что писал другой источник …
  нажмите там Ctrl+C»;
* при запуске печатается своя сборка (`инструмент tools/tx.py, сборка 2026-09-27-b`) — по дате в шапке
  окна сразу видно, какое из двух окон старое;
* источник подписывается номером процесса: `USB-пульт: Zorro [PID 12345]` — по нему видно, кто пишет;
* инструмент каждые 2 секунды сверяет «что послали» с «что лежит в FC»: при расхождении в консоль
  идёт `[!] эмулятор отдаёт не то, что мы посылаем: Рыск: послали 1500, в FC 1000`;
* эмулятор сам считает писателей каналов: если источники **чередуются** (два окна пишут по очереди),
  на `/tx` появляется предупреждение «Каналы пишут несколько источников» со списком и подсказкой
  нажать Ctrl+C в лишнем окне. Одиночная передача управления (страница → инструмент) тревоги
  не вызывает;
* тревога **показывает, какое окно наше, а какое чужое** (по PID из подписи источника) и даёт готовую
  команду: `taskkill /PID 28888 /F`;
* ключ `--kill-others` (он же включён в `run_tx_joystick.bat`) закрывает чужие окна инструмента —
  и при запуске, и по ходу работы: инструмент сам находит их по PID и снимает процесс.

### Биндинг: «Связать (Bind)» — как на настоящем приёмнике

На странице /tx есть кнопки **«Связать (Bind)»** и **«Развязать»** — это то же, что кнопка Bind
на живом приёмнике:

* **«Связать»** — 2 секунды «поиска приёмника» (состояние `binding`): кадров в эфире нет,
  `MSP_RC` отдаёт значения «Этапа 1», полосы на вкладке «Приёмник» стоят. Через 2 секунды
  состояние само становится `bound`, связь поднимается, каналы снова управляются стиками.
* **«Развязать»** — обратное: приёмник кадров не отдаёт, «Этап 1» и флаг
  `ARMING_DISABLED_RX_FAILSAFE`.

Из консоли то же самое: `python tools\tx.py bind` (`--bind-seconds 0` — связать мгновенно) и
`python tools\tx.py unbind`. Через API: `POST /api/rc {"bind": true, "bind_seconds": 2}` и
`{"bind": false}`.

Биндинг — состояние «в эфире», а не конфигурация: во «флеш» не пишется, после перезапуска
эмулятора аппаратура снова связана, а стики в центре.

### Каналы активны только при настроенном приёмнике

Как в настоящей прошивке, приёмник поднимается только тогда, когда во вкладке **«Порты»** на
каком-нибудь UART включена функция **Serial RX** (по умолчанию — UART2, приёмник CRSF). Если
Serial RX выключить и нажать «Сохранить», `rxRuntimeState.channelCount` становится нулевым:

* `MSP_RC` отдаёт **пустой ответ**; страница /tx пишет «приёмник не настроен»;
* на вкладке «Приёмник» полосы каналов пустые (Configurator при `active_channels === 0`
  приглушает их и не показывает значения).

Включаете Serial RX обратно — каналы возвращаются. Это и есть проверка «аппаратура видна
только при правильных «Портах»».

### Способы управления каналами

Три способа:

1. **Страница в браузере** — <http://127.0.0.1:8088/tx> (запускается вместе с эмулятором):
   подключение/отключение аппаратуры, четыре стика ползунками, органы управления AUX по типам
   аппаратуры, кнопки «Стики в центр», «Газ вниз» и «Демо: покачать стики» (7 секунд покачивания —
   удобно смотреть «Предпросмотр»). Клавиши: `←→` крен, `↑↓` тангаж, `A`/`D` рыск, `W`/`S` газ,
   `Space` — центр. AUX 1–2, 5–6, 8–9, 11–12 — **двухпозиционные тумблеры** (1000/2000 мкс),
   AUX 3 и AUX 4 — **трёхпозиционные** (1000/1500/2000, щёлкают по кругу), AUX 7 и AUX 10 —
   **крутилки** (ползунок 1000…2000 мкс).
2. **Консоль** — `tools/tx.py`:

   ```bat
   python tools\tx.py                                  # показать каналы и состояние связи
   python tools\tx.py roll=1700 yaw=1600 aux1=2000     # выставить каналы
   python tools\tx.py 1500 1500 1500 1000              # позиции 0…3: A/E/R/T
   python tools\tx.py center                           # стики в центр
   python tools\tx.py demo                             # 6 секунд покачивания
   python tools\tx.py disconnect                       # «выдернуть USB» (потеря связи)
   python tools\tx.py connect                          # «воткнуть USB» обратно
   ```
3. **Настоящая аппаратура (Zorro, TX16S, любой пульт)** — стики живого пульта двигают каналы
   эмулятора, как будто он связан с приёмником FC.

   **Если стики двигают не свои каналы** (например, рыск попадает в AUX2, а коптер в
   «Предпросмотре» вращается) — раскладка осей не совпадает. Лечится калибровкой:

   ```bat
   python tools\tx.py joystick --detect     # попросит отклонить по одному стику и всё найдёт сам
   ```

   Инструмент по очереди попросит отклонить крен вправо, тангаж вверх, рыск вправо, а затем
   прокачать газ вверх-вниз (ручку оставить вверху) — и **сам ждёт движения**: нажимать ничего не
   нужно, после отклонённого стика он сразу переходит к следующему шагу. Раскладка сохраняется в `tx_map.json` и дальше используется автоматически
   (`--map auto`); незаконченная калибровка (не все четыре стика найдены) **не сохраняется**, чтобы
   «половинчатая» карта не путала каналы.

   Что видно при обычном запуске `joystick`:

   ```
   оси пульта в покое (по ним видно, та ли раскладка):
      ось 0 (X) → Крен: +0.00 (центр)
      ось 1 (Y) → Тангаж: +0.00 (центр)
      ось 2 (Z) → Газ: +0.02 (середина)
      ось 5 (V) → Рыск: +0.00 (центр)
   ```

   Крен, тангаж и рыск в покое обязаны быть в центре; «упор» у них — признак чужой оси. Про газ
   придирок нет: у трещотки ручка стоит где угодно. Настоящее предупреждение приходит на страницу
   /tx и показывается там жёлтой плашкой — видно без консоли. Строка «оси пульта (их нашёл инструмент): Крен — ось 0, Тангаж — ось 1, …»
   на странице показывает, с какой раскладкой сейчас работает инструмент. Если ось «стика» замерла
   на упоре, инструмент предупредит: похоже, это тумблер, а не стик.

   Пошаговая инструкция «подключение реальной аппаратуры по USB» — `docs/HOWTO_real_tx_usb.md`
   (в комплекте есть «кнопочные» запускалки: `run_tx_joystick.bat`, `run_tx_wire.bat`).

   **Вариант А: пульт как USB-джойстик (проще всего, без приёмника и бинда).**

   ```bat
   python tools\tx.py axes                             # какие оси видит система и что на них сейчас
   python tools\tx.py joystick                         # вести каналы стиками пульта
   python tools\tx.py joystick --map roll=0,pitch=1,throttle=2,yaw=3 --invert pitch
   ```

   Библиотеки не нужны: эмулятор читает пульт сам, системным интерфейсом Windows (winmm) — тем
   же, что у «Игровых устройств» (`Win+R` → `joy.cpl`). Ограничение интерфейса Windows: до 6 осей
   и 32 кнопок на устройство (у пульта меньше); «шляпа» (POV) читается и уходит в AUX.

   На пульте: **MODEL SETUP → USB Joystick** (EdgeTX/OpenTX), подключить шнуром к компьютеру.
   Оси 0…3 — стики, свободные оси, кнопки и «шляпа» автоматически уходят в AUX 1…12; `--invert`
   зеркалит выбранные каналы. Пока режим работает, эмулятор считает аппаратуру связанной.

   **Вариант Б: приёмник в USB-UART переходнике (настоящий эфир и настоящий бинд).**

   ```bat
   python -m pip install pyserial
   python tools\tx.py ports                            # какие COM-порты есть
   python tools\tx.py wire --port COM5                 # автоопределение CRSF (420000) / SBUS (100000)
   python tools\tx.py wire --port COM5 --protocol sbus --baud 100000 --invert roll,pitch
   ```

   Приёмник подключается сигнальным проводом к переходнику (для SBUS нужен инвертирующий),
   аппаратура — обычным образом биндится со своим приёмником. Эмулятор разбирает поток байтов:

   * **CRSF** — кадры RC channels packed (`0x16`, 26 байт, CRC8 0xD5), преобразование как в
     `crsfReadRawRC()` из `crsf.c` (`µs = 0.62477120195241 × raw + 881`);
   * **SBUS** — кадры 25 байт (`0x0F … 0x00`, 16 каналов по 11 бит), как `sbusChannelsDecode()`
     в `sbus.c` (`µs = 0.625 × raw + 881`); кадр с флагом failsafe (бит 0x04) — «Этап 1».

   Как только пошли кадры, эмулятор считает, что **бинд состоялся** (`POST /api/rc {"bind": true}`
   с нулевой задержкой). Пропали кадры на секунду или пришёл failsafe-кадр — «Этап 1» и
   предупреждение о потерянной связи на вкладке «Приёмник». Выключили аппаратуру — полосы
   «упали», включили — сразу поехали: ровно то, что видно с настоящим приёмником.

   **Проверка без железа:** `python tools\tx.py selftest` (CRSF + SBUS + разбор потока из COM-порта).

Под капотом — HTTP-ручка `/api/rc`:

```
GET  /api/rc   → {"channels":[…16…],"connected":true,"serial_ok":true,"serial_port":"UART2",
                  "failsafe":false,"active_channels":16,"source":"страница /tx","names":[…],
                  "bind":{"state":"bound","text":"связана (CRSF на UART2)","ready":true}}
POST /api/rc   ← {"roll":1700,"aux1":2000} | {"channels":[…]} | {"reset":true}
                 {"connected":false} | {"bind":true,"bind_seconds":2} | {"bind":false}
               ← {"connected":false}  («выдернуть USB»)  | {"source":"USB-пульт: …"}
```

Каналы нумеруются в порядке прошивки **A/E/R/T**: 0 — крен, 1 — тангаж, **2 — рыск**, **3 — газ**,
4…15 — AUX 1…12. Тумблер «включён» — 2000 мкс, «выключен» — 1000 мкс.

Запрос проверяется **целиком до применения**: если в нём есть неизвестный канал или нечисловое
значение, сервер отвечает `400` с текстом ошибки и не меняет состояние (ни каналы, ни `source`).
Значения вне диапазона не отбрасываются, а приводятся к границам 1000…2000 мкс, как это делает
приёмник.

Типы служебных полей тоже проверяются (`400` и `{"error":…,"state":…}`): `bind_seconds` — число
секунд (не `true` и не `NaN`), `aux_map` — список строк или строка, `rc_map` — объект,
`layout_note` и `source` — строки, `reset`/`connected`/`bind`/`physical` — `true`/`false`,
`control` — `virtual` или `physical`. Кривое значение — отказ **до** изменений, а не обрыв
соединения: сервер отвечает и продолжает работать.

Важно: состояние стиков **не пишется во «флеш»** и не теряется при `Save`/`Reboot` — это не
конфигурация FC, а «положение пальцев на пульте». После перезапуска эмулятора аппаратура снова
в центре, как если бы вы выключили и включили пульт.

## Приоритет состояния над «эхом» (почему правки иногда «не сохранялись»)

Часть вкладок Configurator пишет блоки, которые эмулятор не моделирует (OSD, GPS-конфиг, миксер,
настройки зума, beeper), — для них записанный payload хранится как «эхо» и отдаётся обратно при
чтении. Механизм удобный, но у него есть побочный эффект: **если эхо осталось в `eeprom.json` от
прежней сборки, оно перекрывает живой ответ FC.**

Так было с вкладкой «Конфигурация»: прежние сборки сохраняли в «флеш» эхо `MSP_FEATURE_CONFIG`.
После перехода на смысловой обработчик состояние (`self.features`) обновлялось, но чтение отдавало
старое эхо — SOFTSERIAL и SERVO_TILT включались, а галочки после «Сохранить» возвращались, и
правки выглядели «несохраняемыми».

Что сделано:

* введён список **состоянийных** кодов чтения (`state_based_read_codes()`): ответы на них FC
  строит сам, и эхо для них больше не используется — ни при чтении, ни при загрузке «флеша»;
* при смысловой записи (`MSP_SET_*`, у которого нет пары в `WRITE_TO_READ`, например
  `MSP_SET_FEATURE_CONFIG` → `MSP_FEATURE_CONFIG`) старое эхо удаляется из памяти;
* при старте устаревшее эхо вычищается из «флеша» и удаляется при следующем сохранении
  (в логе: `[FC] «флеш»: устаревшее эхо для кодов 0x0036 отброшено`);
* сквозные (не моделируемые) блоки продолжают работать через эхо — их поведение не изменилось;
* записи портов из старых «флешей» без скоростей больше не ломают ответ вкладке «Порты».

Проверка: `python tools/check_config_tab.py` содержит раздел «СТАРЫЙ «ФЛЕШ»: ЭХО ПРЕЖНИХ СБОРОК
НЕ ДОЛЖНО ГЛУШИТЬ ЖИВЫЕ ЗНАЧЕНИЯ» — он подкладывает эхо-значения (в том числе для фич) и
убеждается, что вкладка видит настоящее состояние, правки видны сразу и переживают перезапуск.

## Вкладка «OSD»

OSD эмулируется как аппаратный экран MAX7456 (SD-видео), как на плате этого стенда.

| Запрос | Код | Что отдаёт |
|---|---|---|
| `MSP_OSD_CONFIG` | 84 | 221 байт: флаги устройства, видеосистема, единицы, тревоги, места 80 элементов, 31 статистика, 2 таймера, 19 предупреждений, 3 профиля, кадр камеры, порог качества связи |
| `MSP_SET_OSD_CONFIG` | 85 | запись: адрес `-1` — общие настройки, `-2` — таймер, иначе номер элемента (u16 + байт экрана) |
| `MSP_OSD_CANVAS` / `MSP_SET_OSD_CANVAS` | 189 / 190 | размер «полотна» OSD (30×16, как SD PAL) |

Важные детали:

* **Счётчики строго как в прошивке 4.5.4** (`osd.h`): 80 элементов, 31 статистика, 19 предупреждений,
  2 таймера, 3 профиля. Configurator читает их из ответа и сопоставляет со своим списком полей —
  если счётчики расходятся, элементы показываются как «UNKNOWN».
* **Нулевые флаги = пустая вкладка.** Раньше эмулятор отвечал `flags = 0`, и вкладка «OSD» была
  пустой: Configurator считает OSD выключенным и не рисует ни элементов, ни настроек. Теперь
  подняты биты «функция OSD» (0), «аппаратный MAX7456» (4) и «устройство найдено» (5) — вкладка
  заполняется сразу после подключения.
* **Раскладка по умолчанию — как у настроенного квада:** напряжение батареи (1,1), предупреждения
  (13,1), таймер 1 (25,1), газ (1,8), высота (1,14), спутники (25,14), имя (13,15), RSSI (1,15).
  Место элемента пакуется как в прошивке: столбец — биты 0…4, строка — 5…9, видимость профиля —
  биты 11…13 (`VISIBLE << профиль`).
* **Заводские значения** повторяют `pgResetFn_osdConfig()`: метрическая система, RSSI-тревога 20 %,
  ёмкость 2200 мА·ч, высота 100 м, порог LQ 80 %, таймеры «включён с начала полёта» и
  «суммарное время моторов» по 10 с, кадр камеры 24×11, включены все предупреждения кроме
  RSSI/LQ/RSSI dBm/over-cap/RSNR, статистика — 8 пунктов (макс. скорость, мин. батарея, мин. RSSI,
  макс. ток, расход мА·ч, blackbox и его номер, таймер 2).
* **Всё сохраняется во «флеше»** (`osd_config` в `eeprom.json`): перетаскивание элементов, галочки
  статистики, тревоги, таймеры и профиль переживают и «Сохранить», и перезапуск эмулятора.
  `defaults` возвращает заводскую раскладку.

Проверка вкладки целиком: `python tools\check_osd_tab.py` — она разбирает ответ тем же порядком
полей, что и Configurator (`osd.js: OSD.msp.decode`), и проверяет запись, сохранение и перезапуск.

## Вкладка «Корректирование в полёте»

Это те самые «настроечные тумблеры»: когда AUX-канал в заданном диапазоне, прошивка меняет
какой-то параметр — RC Rate, экспозицию, силу режима Horizon, выбор профиля рейтов.

| Запрос | Код | Что отдаёт |
|---|---|---|
| `MSP_ADJUSTMENT_RANGES` | 52 | 30 слотов подряд, по 6 байт: канал, начало, конец, функция, канал-переключатель |
| `MSP_SET_ADJUSTMENT_RANGE` | 53 | запись одного слота (его номер — первым байтом) |

Важные детали:

* **В ответе нет байта-счётчика.** Configurator считает слоты как «длина ответа / 6»
  (при API ≥ 1.48 на слот приходится 10 байт — добавляются центр и масштаб). Если ответ короче
  или длиннее, вкладка разберёт его со сдвигом, поэтому эмулятор отдаёт ровно
  `30 × 6 = 180` байт.
* **Первый байт слота прошивка пишет нулём** («was `adjRange->adjustmentIndex`») — так же
  делает и эмулятор; номер слота вкладка берёт по порядку записей.
* **Диапазон — в шагах по 25 мкс:** импульс = `900 + шаг × 25`, шаг 0…48 (900…2100).
  Выключенный слот — это `начало == конец` (вкладка сама снимает галочку у такого слота и
  пишет `900…900`, когда вы гасите слот).
* **С пустой таблицей страница выглядит пустой:** вкладка по умолчанию показывает только
  включённые слоты. Поэтому эмулятор стартует как «настроенный квад» — четыре рабочих слота:

  | Слот | Когда | Что делает | Через канал |
  |---|---|---|---|
  | 1 | AUX1 в 1300…1700 | RC Rate (пошагово) | AUX1 |
  | 2 | AUX2 в 1300…1700 | RC Expo (пошагово) | AUX2 |
  | 3 | AUX3 в 1700…2100 | выбор профиля рейтов | AUX3 |
  | 4 | AUX4 в 1700…2100 | сила режима Horizon | AUX4 |

* **`defaults` возвращает заводскую (пустую) таблицу** — как `pgResetFn_adjustmentRangeConfig()`
  в прошивке; вкладка при этом покажет «Слотов активно 0/30».
* Слоты сохраняются во «флеше» (`adjustment_ranges` в `eeprom.json`) и переживают перезапуск
  эмулятора — как и остальные вкладки.

Проверка целиком: `python tools\check_adjustments_tab.py` — она читает и пишет ровно теми
кадрами, что шлёт вкладка (`MSPHelper.sendAdjustmentRanges`), и разбирает ответ как
`MSPHelper.ts` (длина / 6).

## Вкладка «Чёрный ящик» (DataFlash)

Эмулятор — «борт» с накопителем W25Q128: 4096 секторов по 4 КиБ (16 МиБ). Вкладка читает его
теми же командами, что и настоящий полётный контроллер, поэтому «данные видны» без всяких
настроек — накопитель уже наполнен тестовыми пролётами.

**Важно: `BLACKBOX` — не фича.** В CLI-команде `feature` чёрного ящика нет и быть не должно:
в прошивке 4.5.4 такого бита не существует (`feature.h`), а в списке `featureNames[]`
(`cli/cli.c`) на его старом месте (бит 11) стоит пустая строка. Поэтому
`feature BLACKBOX` отвечает `###ERROR IN feature: INVALID NAME: BLACKBOX` — как на настоящем
борде. Логирование включается **настройкой**, а не фичей:

* `blackbox_device` = `NONE` | `SPIFLASH` | `SDCARD` | `SERIAL` (у нас `SPIFLASH` — «флеш» на плате;
  в `cli/settings.c` это `lookupTableBlackboxDevice`, а `BLACKBOX_DEVICE_FLASH = 1` — из
  `blackbox/blackbox.h`);
* `blackbox_sample_rate` (`1/1`…`1/16`), `blackbox_mode`, `blackbox_high_resolution`,
  `blackbox_disable_*` — поля журнала.

Не путать с **функцией порта** `BLACKBOX` (`FUNCTION_BLACKBOX = 1 << 7` из `serialPortFunction_e`):
она появляется в колонке «Периферия» вкладки «Порты» и нужна только когда
`blackbox_device = SERIAL`. При `SPIFLASH` порты не задействованы — так и должно быть.

| Запрос | Код | Что отдаёт |
|---|---|---|
| `MSP_DATAFLASH_SUMMARY` | 70 | флаги (готов/поддерживается), секторы, размер, **занято** |
| `MSP_DATAFLASH_READ` | 71 | запрос `[адрес u32, длина u16, сжатие u8]` → `[адрес u32, длина u16, 0, данные]` |
| `MSP_DATAFLASH_ERASE` | 72 | `blackboxEraseAll()` — стирает накопитель (кнопка «Стереть») |
| `MSP_BLACKBOX_CONFIG` | 80 | устройство, `rateDenom`, `P ratio`, `sample_rate`, маска выключенных полей |
| `MSP_SET_BLACKBOX_CONFIG` | 81 | запись этих настроек (кнопка «Сохранить») |
| `MSP_SDCARD_SUMMARY` | 79 | нули: SD-карты у платы нет |

Тонкости, из-за которых вкладки «не видят» чёрный ящик у самодельных эмуляторов:

* **Длинный ответ MSP v1.** 4096 байт данных в кадр v1 не влезают (в заголовке длина — один
  байт, `JUMBO_FRAME_SIZE_LIMIT = 255`). Прошивка отдаёт такие ответы «джамбо»-кадром:
  длина `255`, а настоящая — `u16` после заголовка. Эмулятор это умеет (`bfemu/msp.py`).
* **Старый формат запроса.** Если запрос чтения короче 6 байт, прошивка отвечает 128 байтами
  **без** байта сжатия — просто `адрес u32` + данные (`serializeDataflashReadReply`). Эмулятор
  отвечает так же: 132 байта.
* **`P interval` в заголовке лога — целое.** В 4.5.4 `blackboxInit()` пишет
  `blackboxGetPRatio()` как `I interval / P interval` (у нас 32 / 2 = 16), а в `H P interval`
  попадает целое число (2), а не строка `1/2`.

### Что лежит в накопителе

Шесть пролётов — «квад» летает по сценариям, а модель считает стики, ПИД, моторы, ток и
напряжение. Данные кодируются ровно так, как это делает прошивка (`blackbox_encoding.c`:
UnsignedVB, SignedVB, TAG2_3S32, TAG8_4S16, TAG8_8SVB), поэтому лог читает официальный декодер
`blackbox-tools`.

| № | Пролёт | Что в нём видно |
|---|---|---|
| 1 | Взлёт и посадка | набор высоты, висение, снижение и касание — газ, ток, просадка напряжения |
| 2 | Спокойный полёт по прямой | ровный горизонт, медленный ход вперёд — чистые графики |
| 3 | Полёт по квадрату | четыре прямые и повороты на 90° — всплески по крену и рысканию |
| 4 | Проблема с двигателем | третий мотор теряет тягу: просадка оборотов и увод по рысканию |
| 5 | Плохая жёсткость луча | резонанс ≈120 Гц в гироскопе, растущий с газом |
| 6 | Резкие манёвры: бочки и сальто | гироскоп до ~655 °/с, полный ход стиков |

Запись — каждый второй цикл PID (500 Гц при цикле 1 кГц, `H P interval:2`), 500…6200 кадров на
пролёт, формат Data version 2. Заголовок начинается строкой `Firmware revision: Betaflight 4.5.4
(bfemu) BFRVIRTUALFC` — **префикс «Betaflight» обязателен**: по нему `blackbox_decode` понимает
версию прошивки и правильно масштабирует напряжение (иначе `vbat` окажется в 10 раз больше).

### Где живёт «флеш» и как наполнить заново

* Готовый файл — `blackbox_flash.bin` (1 704 320 Б) рядом с `eeprom.json`, плюс
  `blackbox_flash.index.json` с названиями пролётов. В поставке лежит такой же файл
  (`bfemu/data/blackbox_flash.bin`), чтобы первый запуск не ждал сборки: эмулятор просто
  копирует его к себе вместе с индексом.
* **Если готового файла нет или он «не той» частоты, эмулятор собирает его в фоне** (около
  8 секунд) и всё это время отвечает на MSP — вкладка не получает тайм-аут, а накопитель
  показывает то, что в нём уже есть (пустой — ноль занятых байт).
* Смена частоты записи (`MSP_SET_BLACKBOX_CONFIG` → `sample_rate`) запускает пересборку в фоне;
  `H P interval` в новых логах будет соответствовать настройке.
* Настройки записи (`device`, `sample_rate`, маска полей) сохраняются вместе с конфигурацией
  и переживают перезапуск эмулятора, а сама маска раскладывается по 14 настройкам
  `blackbox_disable_*` — ровно как `blackboxConfigureFields()` в прошивке.

### «Один файл — все пролёты» и режим запоминающего устройства

**Почему в файле «один лог».** Прошивка пишет накопитель подряд и одним потоком: все пролёты
лежат в **одном** дампе, разделённые заголовками `H Product:…`. Кнопка «Сохранено в файл…» всегда
сохраняет весь дамп целиком и всегда даёт одно и то же имя (`BTFL_BLACKBOX_LOG_<борт>_<дата>
_<время>_<плата>.BBL`) — оно генерируется Configurator'ом, а не прошивкой. Поэтому после
сохранения видно «один лог»: просмотрщик открывает дамп и показывает первый пролёт.

Где взять остальные:

* во вкладке **«Blackbox Viewer»** список **«Log»** в верхней панели — в нём все шесть пролётов
  одного дампа (он появляется, когда в файле больше одного лога);
* командой CLI `blackbox` — она печатает список пролётов с размерами, длительностью и временем;
* в **режиме запоминающего устройства** — по файлу на пролёт (см. ниже).

**Кнопка «Активировать режим запоминающего устройства».** Это `MSP_SET_REBOOT` (68) с кодом
режима 2 (`MSP_REBOOT_MSC`) — то же, что делает настоящий борт: перезагружается и показывается
компьютеру как флешка. Эмулятор повторяет это честно, но без USB:

1. на запрос отвечает `[режим, готовность]` (`02 01` — «режим ЗУ, накопитель готов»);
2. перестаёт отвечать по MSP (настоящий борт в режиме ЗУ тоже не отвечает — Configurator
   отключится, это нормально);
3. содержимое «флеша» отдаётся на странице эмулятора **`http://127.0.0.1:8088/msc`** —
   по файлу на пролёт (`LOG00001.BBL` … `LOG00006.BBL`, как их пишет прошивка при выгрузке)
   плюс `BLACKBOX_ALL.BBL` (то же, что кнопка «Сохранено в файл»);
4. выйти — кнопка «Выйти из режима запоминающего устройства» на той же странице (у настоящего
   борта для этого передёргивают питание). Через 10 минут эмулятор выходит сам, чтобы не
   «залипнуть»; перезапуск эмулятора тоже выводит из режима.

Каждый `LOG0000N.BBL` — самостоятельный файл: его открывает и просмотрщик Configurator'а, и
`blackbox_decode`.

`blackbox` в CLI тоже подсказывает это в конце вывода:

```
note: all 6 logs are stored in ONE dataflash dump; the viewer switches between them in its 'Log' list
buttons: 'Save to file' writes that dump; 'reboot to MSC' publishes LOG0000N.BBL files on the page /msc
```

### Как проверить

`python tools\check_blackbox.py` — 36 проверок: накопитель, чтение «джамбо»-кадрами, сжатие,
старый формат запроса, настройки и их сохранение, режим запоминающего устройства (ответ на
`MSP_SET_REBOOT`, «молчание» MSP, файлы на `/msc`, сверка с накопителем, выход из режима),
`erase`, `refill`, сверка выкачанных данных с накопителем и прогон официального декодера. Декодер берётся из переменной `BB_DECODE`
(по умолчанию `/tmp/bbtools/obj/blackbox_decode`); если его нет, проверка декодера пропускается.

Секция 14 в `tests/smoke_test.py` повторяет те же шаги по сети — как их делает вкладка.

## Тесты

«сырой» CLI в обоих режимах, запись конфигурации из интерфейса (`MSP_SET_*`),
ребут по `save` и по `MSP_SET_REBOOT`, переподключение и сохранение настроек во «флеш».

Быстрые проверки (`pytest tests`) закрывают в том числе чужие «флеши»: имя профиля вида «BEEF»
после перезапуска остаётся строкой (а не байтами), `defaults` сбрасывает всю конфигурацию,
а валидный JSON с неверной структурой (список вместо объекта, строка вместо списка) не мешает
запуску — разделы читаются поштучно, битые заменяются заводскими значениями.

`tests/test_transport.py` проверяет транспорт по проводу: новое подключение после `save`/`MSP_SET_REBOOT`
действительно ждёт `--boot-delay` (раньше ответ приходил мгновенно), обычное подключение не ждёт
ничего, подвисший «ребут» не держит соединение навсегда, а постраничное чтение CLI не путает
соединения (буфер вывода — у соединения, а не общий на FC). В `test_web_monitor.py` добавились
проверки отказов `400`: кривой тип поля в `/api/rc` (`bind_seconds`, `aux_map`, `rc_map`, `layout_note`,
`source`, флаги, `control`) больше не рвёт соединение, а отвечает JSON'ом и ничего не меняет.
