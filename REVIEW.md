Что осталось открытым (сознательно, с причиной):

* **`VirtualFC` по-прежнему god-class** (7 268 строк). Дробление на модули — это сотни правок в
  работающем коде ради читаемости; делать его стоит отдельной задачей с зелёным CI на входе.
* **Монолит `main()` в `tests/smoke_test.py`** (2 736 строк). Вместо переписывания добавлен
  быстрый pytest-слой; smoke остаётся «сквозным» тестом целиком.
* **CI лежит в [`ci/github-actions-ci.yml`](ci/README.md), а не в `.github/workflows/`** — у токена,
  которым работал агент, нет права `workflows`. Включается одной командой `git mv`, см. `ci/README.md`.
* **TCP-порт 5761 по умолчанию слушает `0.0.0.0`** — это нужно для Configurator в другой ОС/ВМ,
  но в общей сети означает, что подключиться может кто угодно. Задавайте `--tcp 127.0.0.1:5761`,
  если сеть не доверенная.
* **Нет верхней границы длины MSP-кадра** в `msp.py::_parse_one`: злонамеренный клиент может
  заставить буфер расти. Для локального эмулятора некритично, для публичного запуска — нет.
* **17 скриптов `tools/check_*.py` дублируют обвязку** (запуск эмулятора, счётчик провалов).
  Единый каркас напрашивается, но это снова массовая правка рабочего кода.

## 1. Итог

**Общая оценка: 7 / 10 — очень сильное техническое ядро в слабой инженерной «обёртке».**

Это не «ещё один скрипт-заглушка»: эмулятор действительно проходит рукопожатие Betaflight
Configurator, отдаёт 152 MSP-команды, реализует **все 59 команд CLI** прошивки 4.5.4 и 683 настройки,
умеет «флеш», перезагрузку, чёрный ящик с настоящим BBL-кодированием, failsafe-сценарии и виртуальную
аппаратуру. Уровень проработки деталей протокола (префиксы длины строк, порядок бит сенсоров, порядок
портов из `serialPortIdentifiers[]`) — заметно выше среднего для хобби-проекта.

Проседает всё, что лежит *вокруг* кода: один god-class на 7 268 строк, нет упаковки, лицензии, CI,
`.gitignore`, в индексе лежат `.pyc`, лог с путём `C:\Users\Aleksandr`, дубль бинарника на 1,7 МБ, а
собственный тест **падает сразу после клонирования**.

## 3. Сильные стороны

1. **Фиделити протокола, а не «похоже на правду».** В коде и README зафиксированы ровно те ловушки,
   на которых ломается самописный MSP: длина-префикс в `MSP_BOARD_INFO`/`MSP2_GET_TEXT` против голой
   строки в `MSP_NAME`, упаковка сенсоров `acc|baro|mag|gps|rangefinder|gyro` из `msp.c` (а не из
   `sensors.h`), 24-байтный `MSP_STATUS_EX` для API 1.46, `MSP2_COMMON_SERIAL_CONFIG` = **0x1009**,
   биты фич с «дырами» (`SOFTSERIAL = 1 << 6`). Такое знание обычно добывается днями отладки.
2. **Генерация данных из исходников, а не ручной список.** `tools/gen_data.py` (688 строк) разбирает
   дерево Betaflight и строит `bf_data.json`; эмулятор при старте сверяет биты фич (`check_feature_bits`).
   Это защищает от самого частого способа «протухнуть».
3. **Поведение, а не только ответы.** Разрыв линка на `save`/`defaults`/`MSP_SET_REBOOT`, задержка
   загрузки (`--boot-delay`), RAM против «флеша», появление/исчезновение SOFTSERIAL1/2, молчание MSP в
   режиме запоминающего устройства — это моделирование конечного автомата, а не таблица заглушек.
4. **Настоящий чёрный ящик.** `blackbox.py` + `bb_scenarios.py` (1 457 строк) кодируют кадры I/P/S с
   предикторами и tag2_3s32/tag8_4s16 — скачанный файл открывается как обычный BBL-лог.
5. **Отличные эксплуатационные показатели.** Старт 0,63 с, 21 МиБ памяти, 7 288 запросов/с при задержке
   0,14 мс — на три порядка больше, чем нужно Configurator'у. Парсер корректно ресинхронизируется на
   мусоре и молча отбрасывает битую CRC, как прошивка; неизвестные коды получают пустой ответ, чтобы
   клиент не висел в таймауте. Это осознанные инженерные решения.
6. **Ноль зависимостей.** Запуск где угодно, где есть Python 3.10+, — для инструмента, который должен
   «просто завестись» у пилота на Windows, это правильный выбор.
7. **Документация как инженерный журнал.** README честно описывает ограничения («это не симулятор
   физики», «массивы в `dump` пропускаются») — редкость и признак зрелости.

## 4. Проблемы по приоритетам

### P0 — ломает первое впечатление, чинится за час

**P0-1. Собственный тест падает сразу после клонирования.**
`tests/smoke_test.py` проверяет, что `.bat`-файлы — ASCII + CRLF, но в git они лежат с LF:

```
[FAIL] командные файлы .bat: только ASCII и CRLF
       (run_tx_joystick.bat, run_tx_wire.bat, run_windows.bat, run_windows_com.bat, run_windows_debug.bat)
```

Причём в шапке `run_windows.bat` написано: *«cmd.exe mis-parses LF-only batch files, which closes the
window»* — то есть у пользователя Windows окно и правда может закрыться. Нет `.gitattributes`, поэтому
нормализация переводов строк неуправляема. Лечение:

```bash
printf '*.bat text eol=crlf\n*.ps1 text eol=crlf\n*.sh  text eol=lf\n*.py  text eol=lf\n' > .gitattributes
unix2dos run_*.bat && git add --renormalize .
```

**P0-2. `tools/demo_session.py` из «Быстрого старта» README падает.**

```
File "tools/demo_session.py", line 143
    rc = struct.unpack("<8H", link.send_msp(105))
struct.error: unpack requires a buffer of 16 bytes
```

Приёмник по умолчанию CRSF → `MSP_RC` отдаёт 16 каналов, а демо распаковывает 8. Чинится одной строкой
(`struct.unpack(f"<{len(d)//2}H", d)`), но показателен сам факт: каталог `tools/` — это 8 549 строк
(34 % кодовой базы), а тестами затронут **только** `tx.py` (три проверки: `selftest`, `bind`, `wire`);
17 скриптов `check_*.py` (5 809 строк) и `demo_session.py` не проверяет никто. Там же `demo_session`
печатает `цель: \tSTM32F405\tVIRTUALFC\x03BFR` — не разбирает те самые префиксы длины, про которые
предупреждает README.

**P0-3. Мусор в индексе git.** Нет `.gitignore`; закоммичены:
* 11 файлов `bfemu/__pycache__/*.cpython-314.pyc` (чужой байт-код Python 3.14);
* `logs/bfemu.log` — с путём `C:\Users\Aleksandr\Documents\GitHub\bfemu\eeprom.json` (утечка имени
  пользователя, лишний шум в diff);
* `blackbox_flash.bin` (1,7 МБ) + `blackbox_flash.index.json` — **дубликаты** `bfemu/data/*`
  (одинаковый md5 `5cb569f4…`), то есть 1,7 МБ сгенерированного артефакта в истории дважды;
  при этом `eeprom.json` создаётся в корне на каждом запуске и тоже попадёт в коммит.

```bash
printf '__pycache__/\n*.pyc\neeprom.json\nlogs/\n' > .gitignore
git rm -r --cached bfemu/__pycache__ logs blackbox_flash.bin blackbox_flash.index.json
```

### P1 — мешает развитию и приёму кода извне

**P1-1. Три дубликата ключей в карте обработчиков** (`ruff F602`):

| Файл:строка | Ключ | Что происходит |
|---|---|---|
| `fc.py:2802` → `2807` | `MSP_SET_RC_TUNING` | первая запись `self._h_set_echo` **мертва** — её молча затирает настоящий обработчик |
| `fc.py:2733` → `2858` | `MSP2_SET_MOTOR_OUTPUT_REORDERING` | полный дубль |
| `fc.py:2734` → `2859` | `MSP2_SEND_DSHOT_COMMAND` | полный дубль |

Сейчас «повезло»: нужная строка идёт последней. Поменяй автор порядок — запись рейтов из Configurator
тихо превратилась бы в эхо, и поймать это было бы тяжело. Карту стоит собирать с проверкой
`assert key not in table`.

**P1-2. God-class.** `VirtualFC` — 368 методов и **123 поля**, выставляемых в `__init__` на 293 строки,
файл `fc.py` — 7 268 строк. Состояние (настройки, флеш, GPS, моторы, failsafe, VTX, OSD, blackbox,
RX-биндинг) и транспорт живут в одном объекте без границ. Разбиение по доменам
(`state/`, `handlers/telemetry.py`, `handlers/config.py`, `domains/failsafe.py`) — самая полезная
инвестиция на будущее: сейчас любое изменение требует держать в голове весь класс.

**P1-3. Тесты — один скрипт, одна функция.** `smoke_test.py::main()` = **2 736 строк**: нельзя запустить
одну проверку, нет изоляции, при падении на шаге 3 остальные 600 проверок не выполняются, параллельный
прогон невозможен, время — 100 с. Плюс 17 файлов `tools/check_*.py` (5 809 строк) дублируют
обвязку (свой `Client`, свой `check()`, свой запуск сервера) — это та же тестовая пирамида, только
вне тестов. Миграция на pytest с фикстурами `fc`/`client` сократит объём в разы и даст выборочный прогон.

**P1-4. Проект нельзя установить.** Нет `pyproject.toml` → ни `pip install .`, ни `pipx`, ни точки входа
`bfemu`; запуск только из корня репозитория. Нет `LICENSE` — формально права на использование не выданы
никому. Нет CI: `smoke_test` + `ruff` в GitHub Actions ловили бы P0-1 и P1-1 автоматически.

**P1-5. Юридический нюанс.** В `docs/` лежат 1,4 МБ исходников Betaflight и Configurator под **GPLv3**.
Атрибуция в `docs/*/README.md` есть (это плюс), но у самого репозитория лицензии нет, а соседство
GPL-файлов с нелицензированным кодом — серая зона. Варианты: вынести эталоны в скрипт-загрузчик
(`tools/fetch_refs.sh`) или явно оформить репозиторий как GPLv3 + `NOTICE`.

### P2 — безопасность и мелочи

**P2-1. Веб-монитор слушает 0.0.0.0 жёстко, без опции** (`server.py:1058,1065`), TCP по умолчанию тоже
`0.0.0.0:5761`. В общей Wi-Fi-сети любой сосед может дёргать `/api/rc` (стики!), `/sim_flight/on`,
`/msc/exit`. Нужен флаг `--http-host` со значением `127.0.0.1` по умолчанию.

**P2-2. Нет экранирования HTML — проверено, воспроизводится.** Вывод CLI и имена подставляются в
страницу как есть:

```bash
# через MSP2_CLI_COMMAND:
set craft_name = <img src=x onerror=alert(1)>
curl -s http://127.0.0.1:8088/ | grep -c 'onerror=alert(1)'   # → 1, payload уехал в страницу
```

Для локального инструмента это не катастрофа, но `html.escape()` в `_page()`/`pages.py` — пять минут
работы. Там же: изменяющие состояние действия сделаны **GET-ссылками** (`/sim_flight/on`,
`/failsafe/on`, `/msc/exit`), значит срабатывают по простому `<img src>` с любой открытой вкладки.

**P2-3. Линтер.** 127 замечаний `ruff --select E,F` (67 в пакете): 12 неиспользуемых импортов,
8 неиспользуемых переменных, `F821` — несуществующее имя `Flight` в аннотации `blackbox.py:383`
(спасает только `from __future__ import annotations`), 43 `try/except: pass` вместо `contextlib.suppress`,
9 «слепых» `except Exception`. Ничего страшного, но `ruff --fix` + pre-commit снимут весь класс проблем.
*Замечание: правила `RUF001-003` (1 787 штук) — ложные срабатывания на кириллицу, их нужно отключить.*

**P2-4. Документация без структуры.** README — 1 804 строки / 38 разделов, `WINDOWS.md` — 1 863 строки /
45 разделов, из которых 30+ это `## Обновление от 2026-10-…`, то есть **CHANGELOG, спрятанный в
инструкции для Windows**. Пересечения между файлами почти нет (1 %) — дублирования нет, но новичок
не найдёт нужное. Разнести: короткий README (что это, запуск, подключение) + `docs/protocol-notes.md`
+ `docs/tabs/*.md` + `CHANGELOG.md`.

**P2-5. Мелочь протокола.** Кадр с завышенным полем длины подвешивает поток до прихода недостающих байт
(`msp.py:_parse_one` ждёт `total`), последующие валидные кадры съедаются как payload. Прошивка ведёт
себя похоже, так что это допустимо, но таймаут-ресинхронизация (сброс буфера после N мс тишины) сделала
бы линк дружелюбнее.

**P2-6. История git.** Один коммит `first_upload` на 25 тысяч строк: нет возможности понять, почему
принято то или иное решение, `git bisect` бесполезен, ревью по частям невозможно.

## 6. Вывод

По инженерной сути — **это лучший известный мне открытый эмулятор FC на Python**: глубина проработки
MSP/CLI, честная модель «RAM против флеша», настоящий BBL и failsafe-сценарии дают то, ради чего
такой инструмент и заводят — отлаживать Configurator и учить людей без риска для железа.

По форме — это пока **личный проект, выложенный целиком одним коммитом**. Между «работает у автора» и
«может взять кто угодно» лежат примерно два дня работы, и ни один из пунктов не требует переписывания:
упаковка, лицензия, CI, `.gitignore`/`.gitattributes` и распил двух самых больших файлов. После этого
оценка честно выходит на 8,5–9 из 10.
