# Непрерывная интеграция

Проверки разложены по двум файлам:

| Файл | Что в нём | Кто правит |
|---|---|---|
| [`checks.py`](checks.py) | **вся логика**: что запускать, с какими аргументами, что считать провалом | обычный коммит |
| [`github-actions-ci.yml`](github-actions-ci.yml) | эталон рабочего процесса: только «какая машина, какой Python, какую проверку вызвать» | вручную, см. ниже |

Такое разделение — не красота ради красоты. Файлы в `.github/workflows/` GitHub разрешает
менять только токеном с правом `workflows`, которого у агента нет
(`refusing to allow a GitHub App to create or update workflow ... without workflows permission`).
Пока в рабочем процессе одни вызовы `python ci/checks.py <проверка>`, его правят раз в год,
а логика проверок меняется обычным коммитом в этот каталог.

## Как запустить то же самое у себя

```bash
python ci/checks.py all          # всё подряд, от быстрого к медленному (~4 минуты)
python ci/checks.py lint unit    # только то, что нужно сейчас
python ci/checks.py --help       # список проверок с описаниями
```

Недостающие инструменты (`ruff`, `pytest`, `build`) программа ставит сама. Системный Python
обычно защищён от установки пакетов, поэтому запускайте из окружения:

```bash
python -m venv .venv && .venv/bin/pip install -e ".[dev]"
.venv/bin/python ci/checks.py all
```

## Что проверяется

| Проверка | Где в CI | Что делает | Зачем |
|---|---|---|---|
| `lint` | ubuntu | `ruff check .` | замечаний сейчас ноль — любое новое видно сразу |
| `unit` | ubuntu 3.10/3.11/3.12 + windows | `pytest tests -q`, 42 проверки | ~10 секунд, гоняется на каждый коммит |
| `bat` | **windows** | `.bat` только ASCII и CRLF | именно этот дефект ломал проект сразу после клонирования; концы строк появляются при выгрузке из git, поэтому проверка обязана идти на Windows |
| `smoke` | ubuntu | `tests/smoke_test.py`, 617 проверок | настоящий сервер и настоящие MSP-кадры (~100 с) |
| `package` | ubuntu | сборка колеса, установка в чистое окружение, живой ответ `MSP_FC_VARIANT = BTFL` | ловит опечатки в `pyproject.toml`, забытые файлы данных и сломанную точку входа `bfemu` |

## Как обновить рабочую копию процесса

```bash
cp ci/github-actions-ci.yml .github/workflows/ci.yml
git add .github/workflows/ci.yml && git commit -m "ci: синхронизировать рабочий процесс" && git push
```

Через веб-интерфейс: открыть `.github/workflows/ci.yml` → карандаш → вставить содержимое
эталона → Commit. **Держите файлы одинаковыми** — расхождение обнаруживается не сразу,
зато красным в чужом pull request.

## Грабли, на которые уже наступили

* **Русский текст и Windows.** На `windows-latest` Python пишет stdout в кодировке системной
  кодовой страницы (cp1252), и первое же русское слово роняет шаг с `UnicodeEncodeError` —
  независимо от того, что шаг проверял. Лечится `PYTHONUTF8: "1"` и `PYTHONIOENCODING: "utf-8"`
  на уровне всего процесса; `ci/checks.py` вдобавок сам переключает свои потоки на UTF-8.
* **Фоновый процесс в шаге.** Запуск эмулятора без отвода вывода в файл держит шаг до таймаута:
  раннер ждёт закрытия унаследованного потока. В `checks.py` вывод уходит в
  `build/ci-emulator.log`, а процесс снимается в `finally`.
* **Версии экшенов.** `actions/checkout@v4` и `actions/setup-python@v5` работают на Node 20
  и дают предупреждение об устаревании — в эталоне стоят `@v7`.
* **Проверка `.bat` на Linux бессмысленна.** В репозитории файлы хранятся с LF, CRLF им выдаёт
  `.gitattributes` при выгрузке. Воспроизводится только на Windows (или `core.autocrlf=true`).
