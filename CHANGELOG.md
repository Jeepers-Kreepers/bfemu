Записи перенесены из `WINDOWS.md`, где они лежали вперемешку с инструкцией по подключению

## 2026-10-08-c — `vtx` — как в прошивке 4.5.4

**Штамп:** `[FC] сборка 2026-10-08-c`.

**Симптом:** `vtx` отвечал `###ERROR IN vtx: INVALID ARGUMENT COUNT` на любые аргументы,
в том числе без аргументов.

**Решение — порт `cliVtx()` из cli.c 4.5.4:**

* `vtx` без аргументов печатает 10 слотов `vtx i aux band channel power start end`
  (`vtxChannelActivationConditions`, `vtx_control.h`); как с завода — нулевые;
* `vtx <слот> <aux> <band> <channel> <power> <начало> <конец>` пишет слот
  (aux 0…13, band/channel/power — в границах таблицы VTX, диапазон 900…2100) и печатает его;
* меньше шести валидных аргументов — слот обнуляется и печатается INVALID ARGUMENT COUNT,
  индекс вне 0…9 — `INDEX NOT BETWEEN 0 AND 9` (как `cliShowArgumentRangeError`);
* `dump`/`diff` показывают слоты (в diff — только ненулевые), настройка сохраняется
  во «флеш» и переживает перезапуск.

## 2026-10-08-b — пищалка: значения как в прошивке 4.5.4

**Штамп:** `[FC] сборка 2026-10-08-b`.

**Симптом:** `beeper` печатал `Disabled:  RX_LOST  USB  CAM_CONNECTION_CLOSE
RC_SMOOTHING_INIT_FAIL` — четыре «заводских» выключенных сигнала, которых в прошивке нет.

**Причина и решение.** В 4.5.4 поле `beeper_off_flags` отсутствует в reset-шаблоне
(`pg/beeper.c`) → по умолчанию 0, и `beeper` без аргументов печатает `Disabled:  none`.
Теперь так и есть. Заодно по `io/beeper.h`/`pg/beeper.c` выровнены:

* `beacon` по умолчанию — `Disabled:  RX_LOST  RX_SET`
  (`DEFAULT_DSHOT_BEACON_OFF_FLAGS = DSHOT_BEACON_ALLOWED_MODES`, без `USE_RACE_PRO`);
* тон DShot-пищалки в `MSP_BEEPER_CONFIG` — 1 (`dshotBeaconTone` из reset-шаблона), а не 0;
* `MSP_SET_BEEPER_CONFIG` (185) разбирается по смыслу: правка во вкладке «Конфигурация»
  видна в CLI `beeper`/`beacon` и наоборот (раньше запись хранилась эхом и интерфейсы
  расходились);
* демонстрация failsafe: бипер `RX_LOST` звучит с точки отката (как `failsafe.c`:
  `!receivingRxData` становится false после страж-времени), и только если сигнал не
  выключен в `beeper_off_flags` (как `beeper()` в `io/beeper.c`).

**Переезд старых настроек:** если во «флеше» (`eeprom.json`) лежит ровно старый заводской
набор выключенных сигналов или пустой набор DShot-бикона, при старте он подменяется
прошивочным. Осознанно сохранённые наборы не трогаются.

## 2026-10-08 — демонстрация failsafe: кнопка, точка отката, «Этап 2» и GPS-спасение

**Штамп:** `[FC] сборка 2026-10-08-a`.

**Что нового:** интерактивная демонстрация failsafe для занятий — целиком машина фаз
прошивки 4.5.4, запускается кнопкой.

* **Страница `/failsafe`** (кнопка «Открыть демонстрацию» на мониторе): кнопки «Потерять
  сигнал» / «Вернуть сигнал» / «Сброс демо», «Взлететь» / «Стоять на земле (взведён)» /
  «Выключить моторы», таймлайн с меткой **ТОЧКА ОТКАТА** и плашкой «откат возможен /
  невозможен», журнал с таймкодами, таблица «параметр → что делает сейчас» и панель
  GPS-спасения с 16 параметрами.
* **Машина фаз — порт `failsafe.c` / `rx.c` / `rc_controls.c` / `gps_rescue.c` 4.5.4:**
  300 мс удержания кадров → «Этап 1» (rxfail, страж-время `failsafe_delay` 1.5 с) → точка
  отката → «Этап 2» (`AUTO-LAND` с `off_delay` 1 с, `DROP`, `GPS-RESCUE`) → моторы в 0 и
  `ARMING_DISABLED_FAILSAFE` → возврат сигнала через `failsafe_recovery_delay`. Тумблер

* **CLI `sim_failsafe`:** `on|off`, `loss|restore|reset`, `arm|disarm`, `box on|off`,
  `switch 0|1|2`, `scenario none|low_sats|hover_low`, `procedure auto-land|drop|gps-rescue`,
  `scale 1|0.5|0.25`, `status` — латиницей, для консоли Configurator.
* **GPS-спасение с проверками:** фазы `ATTAIN_ALT → ROTATE → FLY_HOME → DESCENT → LANDING →
  COMPLETE`; сценарии «мало спутников» (`ABORT` при `sanity checks = FS_ONLY` и потерянной
  связи) и «газа зависания не хватает» (10 с без набора высоты → посадка на месте).
* **Исправлено по ходу проверки:** кнопки режима тумблера (`/failsafe/switch/N`) были
  мертвы — маршрута в `server.py` не было; а сочетание «STAGE2, затем KILL» зацикливало
  машину фаз: в ветке KILL не задавался заново период восстановления (в `failsafe.c` там
  `receivingRxDataPeriodPreset = rxDataRecoveryPeriod`). Теперь KILL отрабатывает мгновенно
  и выходит по снятию тумблера; в машине фаз есть страховка от зацикливания.

## 2026-10-07 — команда `resource`: ресурсы, таймеры и DMA как в 4.5.4

**Штамп:** `[FC] сборка 2026-10-07-a`.

**Симптом:** во вкладке CLI команда `resource` отвечала
`###ERROR IN resource: INVALID ARGUMENT COUNT`. **Причина:** эмулятор знал про ресурсы только
заголовок таблицы, а самой команды `cliResource()` 4.5.4 не было — аргументы ей просто
не подходили.

**Что сделано:**

* **`resource`** — полная команда прошивки 4.5.4 (`cliResource()`): без аргументов печатает
  назначенные пины (`resource MOTOR 1 A00`), `resource show` — таблицу «пин: владелец»
  с заголовком и 20 тире, `resource show all` — ещё активные таймеры и DMA.
  Назначение и освобождение — `resource MOTOR 5 B10` → `Resource is set to B10`,
  `resource MOTOR 5 none` → `Resource is freed`; занятый пин помечается
  `NOTE: B07 already assigned to I2C_SDA 1.`; ошибки дословно прошивочные
  (`INVALID RESOURCE NAME: 'NOGA'`, `INDEX NOT BETWEEN 1 AND 8`, `PARSING FAILED`).
  Имя сверяется как `strncasecmp()` в прошивке — аргумент должен начинаться с полного имени
  ресурса, поэтому `LED` и `LED_STRIP` больше не путаются.
* **Назначенные пины живут во «флеше»**: `save`/`MSP_EEPROM_WRITE` их сохраняют, после
  перезапуска борт поднимается с теми же пинами, `defaults` возвращает заводскую таблицу.
* **`timer` и `dma`** печатают задания как `printTimer()`/`printDmaopt()` 4.5.4 — парами строк:
  `timer A00 AF1` + `# pin A00: TIM2 CH1 (AF1)`, `dma UART_TX 1 0` +
  `# UART_TX 1: DMA2 Stream 7 Channel 4`. Работают `timer show`, `timer A00 list`,
  `dma ADC 1`, `dma pin A00`, а также `dma show`. Смена задания отвечает ошибкой эмулятора:
  потоки у виртуальной платы распаяны жёстко.
* **`dump` и `diff`** теперь содержат секции `# resources`, `# timer`, `# dma` на том же месте,
  что в `printConfig()` прошивки (после имени борта): в дампе видны и свободные слоты
  (`resource MOTOR 5 NONE`, `dma UART_RX 3 NONE`), в `diff` — только изменённые назначения.

## 2026-10-06 — питание живое: «виртуальный полёт»

**Штамп:** `[FC] сборка 2026-10-06-a`.

**Симптом:** «Состояние питания» на вкладке «Питание и батарея» не живое: «Ток потребления
0.00 А», «Израсходовано mAh 0 mAh», цифры не меняются. Так и было: эмулятор считал ток только
с моторов, а на столе моторы стоят, значит ток ровно нулевой и расход не растёт.

**Что сделано:**

* **Ток электроники.** Борт всегда что-то ест: FC, приёмник, VTX и LED — ≈0.55 А с «дыханием»
  0.49…0.61 А. На вкладке это видно сразу, ещё до всякого полёта, а «Израсходовано mAh»
  начинает тикать.
* **Виртуальный полёт** — кнопка на мониторе (<http://127.0.0.1:8088/>, карточка «Питание и
  батарея») или команда CLI `sim_flight on`. Газ идёт по сценарию: взлёт, висение с
  подруливанием, «газ в пол» каждые 25 с. Ток 3…27 А, напряжение проседает и падает по мере
  разряда, расход растёт на глазах, моторы (обороты, температура, ток ESC на вкладке «Моторы»)
  крутятся из того же сценария — цифры на вкладках сходятся.
* **Время эмулятора ×10** — иначе всё было бы физически верно, но цифры менялись бы раз в
  минуту. Масштаб меняется командой `sim_flight scale <1..600>` (например, `scale 60` — «час
  за минуту»).
* **Батарея разряжается и меняется сама.** Когда расход доходит до ёмкости (`bat_capacity`,
  1500 мА·ч по умолчанию), борт садится (газ убирается за 2.5 с), затем ставится новая батарея:
  счётчик мА·ч обнуляется, напряжение снова 4.20 В на банку. Вкладка проходит весь цикл:
  OK → «ПРЕДУПРЕЖДЕНИЕ» → посадка → новая батарея.
* **Остановить** — «■ остановить полёт» на мониторе или `sim_flight off`: моторы падают на 1000,
  ток возвращается к току электроники. «сбросить расход» / `sim_flight reset` обнуляют счётчик.
* Пока идёт полёт, слайдеры вкладки «Моторы» игнорируются (газ держит сценарий, как `mixer.c`
  на взведённом борде). После `save`/`reboot` борт снова «на столе»: полёт — не конфигурация.

**Проверка:**

```bat

python tests\smoke_test.py        :: 610 проверок: раздел 13в — 23 проверки «виртуального полёта»
```

Итог: **47 проверок, 0 провалов**, смоук-тест — **610 OK**. Остальные вкладки перепроверены
(моторы 51, режимы 73, приёмник 87, PID 132, чёрный ящик 33 — провалов нет).

## 2026-09-29 — CLI: команды прошивки 4.5.4 и профиль батареи

**Штамп:** `[FC] сборка 2026-09-29-k`.

**Симптом 1:** команда `profile` во вкладке CLI отвечала
`###ERROR IN input: UNKNOWN COMMAND, TRY 'HELP'`. **Причина:** в эмуляторе были только
«свои» команды, а большей части команд из `cmdTable[]` прошивки 4.5.4 не было вовсе.

**Что сделано:** распознаются **все 59 команд** из `cmdTable[]` 4.5.4 (плюс четыре команды
эмулятора: `blackbox`, `board`, `osd_layout`, `uid`). Вывод сверен построчно с исходником
`src/main/cli/cli.c` тега 4.5.4, состояния — в тех же таблицах, что видят вкладки:

* `profile` без аргумента печатает активный профиль (`profile 0`), `profile 2` переключает,
  вне 0…3 — `PROFILE OUTSIDE OF [0..3]`; `rateprofile` — то же для рейтов;
* `rxfail` — 18 каналов, значение по сетке 25 мкс с прижатием к 750…2250 (`constrain`);
* `rxrange` (4 канала, `reset`), `adjrange` (30 слотов, 900 + 25·шаг мкс), `motor`
  (1000…2000, `255` — все), `mmix` (`1.000`, `reset`, `load`), `dshotprog` (`Command Sent: %d`),
  `dshot_telemetry_info` (таблица ESC);
* `led` — 32 строки `x,y:направления:функции+наложения:цвет`, `color` — 16 цветов HSV,
  `mode_color` — 48 строк;
* `beeper`/`beacon`, `play_sound`, `flash_read`/`flash_write`/`flash_erase`/`flash_scan`,
  `rc_smoothing_info`, `sd_info`, `signature`, `bind_rx`, `simplified_tuning`;
* `escprog`, `gyroregisters`, `serialpassthrough` отвечают `NOT SUPPORTED IN THIS EMULATOR` —
  это честная ошибка эмулятора вместо прежнего `UNKNOWN COMMAND`.

**Симптом 2:** «не могу найти `battery_profile`». **Причина:** в прошивке 4.5.4 профилей
батареи нет вообще — это функция мастера BF (будущая 4.6); в Configurator выбор профиля
появляется только при MSP API ≥ 1.48, а эмулятор представляется как 4.5.4 (API 1.46).

**Что сделано:** `battery_profile` добавлена по мастер-исходникам: без аргумента печатает
активный, `battery_profile 0…2` переключает, вне диапазона — `BATTERY PROFILE OUTSIDE OF
[0..2]`; три профиля (пороги ячеек, ёмкость, число банок, процент предупреждения, имя до
8 символов) хранятся в `eeprom.json`; работают `MSP2_BATTERY_PROFILE`/`MSP2_SET_BATTERY_PROFILE`
(0x300E/0x300F), бит `0x40` в `MSP_SELECT_SETTING` и `MSP2_GET_TEXT`/`SET_TEXT` тип 11.
Выбор профиля в окне Configurator потребует поднять API до 1.48 — это отдельный раунд
(подробности в README, раздел «Профили батареи»).

## 2026-09-29 — монитор: адрес, порт и «страница не открывается»

**Штамп:** `[FC] сборка 2026-09-29-h`.

Если монитор «не виден», дело в трёх вещах — теперь все три видны по логу:

* **Веб-страницы поднимаются только с ключом `--http`.** `run_windows.bat` передаёт
  `--http 8088` сам, поэтому страница живёт на <http://127.0.0.1:8088/>. Если запустить
  `python -m bfemu` без ключа, MSP-порт работает, а страниц нет — и теперь об этом прямо
  написано в логе: `веб-монитор и /tx выключены … добавьте --http 8088`.
* **Порт веб-монитора занят** (например, старый экземпляр эмулятора ещё жив) — раньше

## 2026-09-27 — вкладка «Корректирование в полёте» заполнена

**Штампы:** `[FC] сборка 2026-09-27-c, страница аппаратуры v8`.

**Симптом:** вкладка **«Корректирование в полёте»** открывалась пустой — ни одного слота.

**Причина.** Эмулятор не отвечал на `MSP_ADJUSTMENT_RANGES` (52) и `MSP_SET_ADJUSTMENT_RANGE`
(53) — на неизвестный код уходил пустой ответ. Вкладка получала «0 слотов», а так как она
показывает только **включённые** слоты, страница оставалась пустой. Заводская таблица в
прошивке вообще пустая: `pgResetFn_adjustmentRangeConfig()` оставляет все 30 слотов выключенными
(включённым считается слот, у которого начало диапазона не равно концу).

**Что теперь.** `MSP_ADJUSTMENT_RANGES` отдаёт все 30 слотов по 6 байт — ровно `30 × 6 = 180`
байт, без байта-счётчика (Configurator считает слоты как «длина ответа / 6»; при API ≥ 1.48 на
слот приходится 10 байт). Запись `MSP_SET_ADJUSTMENT_RANGE` разбирается и сохраняется.

Таблица заполнена как у настроенного квада — четыре рабочих слота, их видно сразу:

| Слот | Когда | Что делает | Через канал |
|---|---|---|---|
| 1 | AUX1 в 1300…1700 | RC Rate (пошагово) | AUX1 |
| 2 | AUX2 в 1300…1700 | RC Expo (пошагово) | AUX2 |
| 3 | AUX3 в 1700…2100 | выбор профиля рейтов | AUX3 |
| 4 | AUX4 в 1700…2100 | сила режима Horizon | AUX4 |

Диапазоны — в шагах по 25 мкс (`импульс = 900 + шаг × 25`), как в прошивке. Правки вкладки
(галочка «если включено», канал, границы, функция, канал-переключатель) сохраняются по
«Сохранить» во «флеш» и переживают перезапуск эмулятора. Команда `defaults` возвращает
заводскую пустую таблицу — вкладка покажет «Слотов активно 0/30».

Проверка: `python tools\check_adjustments_tab.py` (читает и пишет теми же кадрами, что
`MSPHelper.sendAdjustmentRanges`, и разбирает ответ как `MSPHelper.ts`).

## 2026-09-27 — вкладка «OSD» больше не пустая

**Штампы:** `[FC] сборка 2026-09-27-b, страница аппаратуры v8`.

**Симптом:** вкладка **OSD** в Configurator открывалась пустой — ни элементов, ни настроек.

**Причина.** Configurator считает OSD выключенным, если в ответе `MSP_OSD_CONFIG` пришёл нулевой
байт флагов: `osd.js` делает `haveSomeOsd = flags !== 0` и в этом случае не рисует ничего.
Эмулятор отвечал именно так (8 байт и `flags = 0`), к тому же без списка элементов — разбор ответа
падал на середине.

**Что теперь.** `MSP_OSD_CONFIG` отдаёт полные 221 байт: флаги (функция OSD + аппаратный MAX7456 +
устройство найдено), видеосистема, единицы, тревоги, места **80 элементов**, **31** статистика,
**2** таймера, **19** предупреждений, **3** профиля, кадр камеры 24×11 и порог LQ 80 % — счётчики
взяты из `osd.h` 4.5.4, поэтому Configurator показывает свои обычные подписи, а не «UNKNOWN».

Раскладка по умолчанию — как у настроенного квада: напряжение батареи, предупреждения, таймер,
газ, высота, спутники, имя дрона и RSSI. Видеоформат, единицы, тревоги, элементы, статистика,
таймеры, профили и полотно OSD (30×16) правятся во вкладке и сохраняются: «Сохранить» →
`MSP_SET_OSD_CONFIG` + `MSP_EEPROM_WRITE` → и после перезапуска эмулятора всё на месте.
`defaults` возвращает заводскую раскладку.

Проверка: `python tools\check_osd_tab.py` (читает и пишет ровно теми кадрами, что шлёт вкладка:
`stores/osd.ts` — encodeOther / encodeLayout / encodeTimer / encodeStatisticsPayload).

## 2026-09-27 — калибровка AUX: тумблеры и крутилки

**Штамп:** страница аппаратуры **v8**.

Стики калибровались давно (`--detect`), а тумблеры и крутилки — нет: свободные оси просто
уходили в AUX-каналы, и назначить на них режимы было нельзя. Теперь есть отдельная калибровка AUX.

**Как это выглядит:**

```
python tools\tx.py joystick --detect-aux

Калибровка AUX: тумблеры и крутилки. Нажимать ничего не надо.
   • переведите тумблер во ВСЕ его положения (щёлк-щёлк) — для трёхпозиционного пройдите все три;
   • крутилку покрутите до упоров в обе стороны;
   • когда переключать больше нечего — просто подождите 8 секунд, я закончу.
   что видно в покое:
   • ось 3 (R) в покое на упоре (-1.00) — похоже, это тумблер (или ось, которую пульт не отдаёт)
   Шаг 1: переключите ЛЮБОЙ ещё не найденный тумблер или крутилку (жду 8 с)
      нашёл: ось 3 (R) → AUX1, тумблер (2 положения), положения 1000 / 2000 (на пульте это обычно CH4)
      нашёл: ось 4 (U) → AUX2, тумблер (3 положения), положения 1000 / 1500 / 2000 (обычно CH5)
   найдено 2: AUX1 ← тумблер (2 положения) — ось 3, AUX2 ← тумблер (3 положения) — ось 4
```

Что делает инструмент:

* сам видит, какая ось шевельнулась, и **по характеру движения определяет тип**: две устойчивые
  позиции — тумблер на 2 положения (1000/2000), три — на 3 положения (1000/1500/2000),
  плавное изменение — крутилка (1000…2000 линейно, ход калибруется до упоров);
* назначает каналы **по порядку**: первый найденный тумблер → AUX1 (CH5), второй → AUX2 (CH6)…
  Номер можно задать вручную: `--aux-map 3=switch2:3`;
* сохраняет раскладку в `tx_map.json` (рядом со стиками) — при следующем запуске она подхватывается
  сама, повторять калибровку не нужно;
* печатает раскладку при запуске и отправляет её на страницу `/tx` — она видна в карточке
  «Состояние» строкой `AUX-каналы: …`;
* если ось за всю калибровку не шевельнулась, пишет прямо: «в режиме USB Joystick пульт отдаёт
  только назначенные каналы — проверьте MODEL SETUP → MIXES».

**Если тумблеры не определяются вообще.** Чаще всего они просто не назначены на каналы в микшере
пульта: в режиме USB Joystick EdgeTX/OpenTX отдаёт по USB только те каналы, которые есть в модели.
На пульте: `MODEL SETUP → MIXES` → добавить тумблеру канал (`CH5`, `CH6`, …) → заново
`python tools\tx.py joystick --detect-aux`. Проверить, что канал «поехал», можно так:
`python tools\tx.py axes` — щёлкайте тумблерами и смотрите, какая ось меняется.

Команды:

| Команда | Что делает |
|---|---|
| `python tools\tx.py joystick --detect` | калибровка стиков, а сразу за ней — тумблеров и крутилок |
| `python tools\tx.py joystick --detect-aux` | только AUX (стики берутся из сохранённой раскладки) |
| `python tools\tx.py joystick --detect --no-aux` | только стики (как раньше) |
| `python tools\tx.py joystick --aux-map none` | сбросить раскладку AUX (каналы снова в покое 1000) |
| `python tools\tx.py joystick --aux-map 3=switch2,4=switch3:4,5=knob:7` | задать вручную: ось 3 — тумблер на AUX1, ось 4 — трёхпозиционный на AUX4, ось 5 — крутилка на AUX7 |

## 2026-09-26 — раскладка осей: калибровка стала автоматической, предупреждение видно на странице

Симптом, из-за которого это сделано: после «Подключить аппаратуру» стик Рыск двигает не рыск, а
AUX, и коптер в «Предпросмотре» постоянно крутится. Это значит, что раскладка осей вашего пульта
не совпадает с той, с которой работал инструмент.

**0. Что показал реальный пульт (Zorro, лог калибровки).** Оси у него такие: X — крен, Y — тангаж,
Z — газ, Rz (ось 5) — рыск, а оси 3 и 4 не двигаются вовсе. Прежнее предупреждение «газ в центре —
раскладка не та» оказалось **ложной тревогой**: у газа трещотка, и в покое ручка может стоять где
угодно, в том числе в середине. Из-за него на странице /tx висела жёлтая плашка при верной
раскладке. Теперь про газ предупреждений нет вообще, а проверяются только те признаки, которые
однозначны: стики крена, тангажа и рыска сами возвращаются в центр, поэтому «стик на упоре»
означает чужую ось.

**1. Калибровка теперь сама ждёт движения стика.** Раньше нужно было успеть отклонить стик и
нажать Enter — при спешке шаг пропускался, и сохранялась «половинчатая» раскладка (а из-за неё
свободные оси раздавались в AUX — тот самый «рыск в AUX2»). Теперь так:

```bat
python tools\tx.py joystick --detect
```

* четыре шага: крен вправо → тангаж вверх → рыск вправо → газ (прокачать вверх-вниз и оставить
  ручку вверху). Газ идёт последним: у него трещотка, ось ищется по размаху движения, а не по
  положению в покое. В подсказках написано, какой это стик (правый/левый);
* после подсказки просто отклоните стик до упора — инструмент увидит движение и **сам** перейдёт
  к следующему шагу (нажимать Enter между шагами не нужно);
* если шаг не определился, раскладка **не сохраняется** и инструмент прямо об этом говорит —
  «половинчатая» карта больше не может испортить каналы;
* старая неполная `tx_map.json` (если она у вас осталась) теперь игнорируется: берётся AETR и
  печатается предупреждение «откалибруйте заново».

**2. Инструмент сам проверяет раскладку и говорит о ней.** При запуске `joystick` печатается,
где покоится каждая ось и какому каналу она отдана:

```
оси пульта в покое (по ним видно, та ли раскладка):
   ось 0 (X) → Крен: +0.00 (центр)
   ось 1 (Y) → Тангаж: +0.00 (центр)
   ось 2 (Z) → Газ: +0.02 (середина)
   ось 5 (V) → Рыск: +0.00 (центр)
```

Смотрите на крен, тангаж и рыск: они в покое обязаны быть **в центре**. Если у одного из них
написано «упор внизу/влево» или «упор вверху/вправо» — вот это настоящий признак, что каналу
отдана чужая ось, и инструмент скажет об этом сам (и покажет плашку на /tx). Про газ придирок
нет: трещотка останавливает ручку где угодно.

**3. Это же предупреждение видно на странице /tx** — жёлтой плашкой в карточке «Подключение
аппаратуры». Если инструмент ещё не запускали, там написано «раскладка осей пульта пока не
приходила» — тогда страница просто не знает ваших осей.

**4. `run_tx_joystick.bat` теперь в три шага** и подсказывает самое важное: какие устройства
нашлись (если джойстиков несколько — выберите свой ключом `--index N`) и что ось газа в покое
должна быть внизу.

**Если стики по-прежнему двигают не то — по шагам:**

1. `python tools\tx.py axes` — убедитесь, что инструмент видит именно ваш пульт (список устройств
   с номерами; при нескольких — `--index N`).
2. `python tools\tx.py joystick --detect` — пройдите четыре шага калибровки.
3. Посмотрите, что инструмент печатает перед стартом: у крена, тангажа и рыска должно быть
   **«центр»**; у газа — как угодно (трещотка).
4. Откройте страницу /tx: в карточке «Подключение аппаратуры» строка «оси пульта (их нашёл

## 2026-09-25 — один хозяин у каналов + калибровка осей пульта

**1. Больше нет «срывов», когда работают и пульт, и ползунки.** У каналов всегда один хозяин —
и правило работает в обе стороны:

* нажато **«Отключить (выдернуть USB)»** (обычное состояние) — данные пульта **отклоняются**
  (HTTP 409), инструменты пишут «управление каналами сейчас у страницы /tx» и ждут, пока
  управление вернут;
* нажато **«Подключить аппаратуру»** — каналами владеет пульт, и наоборот: страница и скрипты
  ничего не пишут, их запись тоже отклоняется (409) — ползунки не могут дёрнуть стики пульта;
* сама страница пишет каналы, когда управление у неё.

**2. Калибровка осей: если стики двигают не свои каналы.** Симптом: двигаете рыск — едет AUX2,
а коптер в «Предпросмотре» бешено вращается (значит, крен/тангаж/рыск попали на чужие оси).

```bat
python tools\tx.py joystick --detect
```

Инструмент попросит отпустить стики, затем по очереди: крен вправо, тангаж вверх, газ вверх,
рыск вправо — и сам определит ось и направление каждого стика. Результат сохраняется в
`tx_map.json` и используется при следующих запусках (`--map auto`). Текущая раскладка теперь
видна и на странице /tx: «оси пульта: Крен — ось 0, Тангаж — ось 1, … (зеркалится)».

Если ось «стика» стоит на упоре больше двух секунд, инструмент предупредит:
«похоже, это тумблер, а не стик» — верный признак, что раскладка неверна.

Вручную, как раньше: `python tools\tx.py joystick --map roll=0,pitch=1,throttle=2,yaw=3 --invert pitch`.

**3. Мелочь для надёжности тестов:** `tests\smoke_test.py` теперь ругается, если на его порту
отвечает чужая копия эмулятора (это спасало от «непонятных» провалов) — перед прогоном лучше
закрыть лишние окна эмулятора.

Самопроверка: `python tools\check_receiver_tab.py`, `python tests\smoke_test.py` (448 проверок).

## 2026-09-25 — страница аппаратуры: кто управляет, бинд, разные AUX

Страница <http://127.0.0.1:8088/tx> теперь ведёт себя как настоящий стенд.

**Кто управляет каналами:**

| Кнопка | Что происходит |
|---|---|
| **Подключить аппаратуру** | управление переходит к настоящей аппаратуре (пульт по USB или приёмник в COM-порту), ползунки/тумблеры/крутилки на странице гаснут |
| **Отключить (выдернуть USB)** | настоящая аппаратура отсоединена, управление возвращается странице — ползунки активны снова |
| **Связать (Bind)** | создаёт связь с контроллером: только после бинда каналы активируются (до этого на вкладке «Приёмник» «Этап 1» и предупреждение о потерянной связи) |

Порядок: «Подключить аппаратуру» → запустить `run_tx_joystick.bat` (пульт) или `run_tx_wire.bat`
(приёмник) → «Связать». Для виртуальной аппаратуры то же: после «Отключить» нажмите «Связать»,
чтобы каналы снова пошли.

**Органы управления AUX — как на аппаратуре:**

* AUX 1–2, 5–6, 8–9, 11–12 — двухпозиционные тумблеры (1000/2000 мкс);
* **AUX 3 и AUX 4 — трёхпозиционные** (1000/1500/2000, щёлкают по кругу мышью, среднее положение
  подсвечено жёлтым);
* **AUX 7 и AUX 10 — крутилки** (плавный ползунок 1000…2000 мкс).

Из консоли всё то же: `python tools\tx.py control virtual|physical`, `bind`, `unbind`,
`aux3=1500`, `aux7=1730`. Типы AUX отдаются в `/api/rc` (`aux_types`) — их можно проверить
командой `python tools\tx.py` или на странице монитора.

Самопроверка: `python tools\check_receiver_tab.py` (раздел про управление и AUX) и
`python tests\smoke_test.py` (448 проверок, раздел 20).

## 2026-09-25 — живая аппаратура: бинд, USB-пульт Zorro, приёмник в COM-порту

Теперь каналы можно вести **настоящей аппаратурой** — стики живого пульта двигают полосы на
вкладке «Приёмник» и модель в «Предпросмотре», а связь ведёт себя как у настоящего приёмника.

Что изменилось в поставке: `bfemu\fc.py`, `bfemu\server.py`, `bfemu\tx_page.py`, `tools\tx.py`,
`tools\check_receiver_tab.py`, `tests\smoke_test.py`, `README.md`, `WINDOWS.md`.

1. **Распакуйте архив поверх** `C:\bfemu`.
2. **Остановите** эмулятор (Ctrl+C) и запустите заново: `run_windows.bat`.

### 1. Кнопка «Связать (Bind)» (как на приёмнике)

На странице <http://127.0.0.1:8088/tx> появились **«Связать (Bind)»** и **«Развязать»**:

| Нажали | Что видно на вкладке «Приёмник» |
|---|---|
| «Связать (Bind)» | 2 секунды «поиск приёмника», кадров нет — «Этап 1» и предупреждение о связи; потом связь поднимается и полосы оживают |
| «Развязать» | приёмник кадров не отдаёт: «Этап 1», флаг потери связи |
| «Подключить аппаратуру» | связь сразу, без поиска |

Из консоли: `python tools\tx.py bind` (или `--bind-seconds 0` — мгновенно), `python tools\tx.py unbind`,
показать состояние — просто `python tools\tx.py`. Биндинг не пишется в «флеш»: после перезапуска
эмулятора аппаратура снова связана.

### 2. Настоящий пульт (Zorro) как USB-джойстик — самый простой путь

Пошаговая инструкция (шаги 1…6 и таблица «если что-то не так») — файл
**`docs\HOWTO_real_tx_usb.md`** в папке эмулятора.

Самый быстрый способ: включите на пульте режим **USB Joystick** (EdgeTX/OpenTX: MODEL SETUP →
USB Joystick), подключите шнур и запустите двойным щелчком **`run_tx_joystick.bat`** — он покажет
оси и начнёт вести каналы (Ctrl+C — стоп). **Библиотеки не нужны вообще**: пульт читается
встроенным способом Windows (системный интерфейс winmm) — ровно то, что видят «Игровые
устройства» (`Win+R` → `joy.cpl`).

Вручную:

```bat
python tools\tx.py axes        :: посмотреть, какие оси у пульта и что на них сейчас
python tools\tx.py joystick    :: вести каналы стиками пульта
python tools\tx.py joystick --map roll=0,pitch=1,throttle=2,yaw=3 --invert pitch
```

На пульте: **MODEL SETUP → USB Joystick** (EdgeTX/OpenTX), затем шнур в компьютер. Ось 0 — крен,
1 — тангаж, 2 — газ, 3 — рыск; свободные оси и кнопки уходят в AUX 1…12. `axes` показывает живые
значения осей — по ним удобно подобрать `--map`. Выход — Ctrl+C (стики вернутся в центр).

### 3. Приёмник в USB-UART переходнике — настоящий эфир и настоящий бинд

Если аппаратура биндится со своим приёмником, а приёмник подключён переходником:

```bat
python -m pip install pyserial
python tools\tx.py ports                                  :: какие COM-порты есть
python tools\tx.py wire --port COM5                       :: CRSF (420000) и SBUS (100000) — авто
python tools\tx.py wire --port COM5 --protocol sbus --baud 100000
```

Быстрый запуск: **`run_tx_wire.bat`** — поставит `pyserial`, покажет список COM-портов, спросит
порт и начнёт читать приёмник.

Пока идут кадры — аппаратура считается связанной, каналы идут в эмулятор. Пропали кадры на
секунду или пришёл SBUS-кадр failsafe — «Этап 1» и предупреждение: ровно как на живом стенде
(выключили пульт — полосы упали, включили — поехали).

### 4. Проверки

```bat
python tools\tx.py selftest            :: CRSF + SBUS + разбор потока из COM-порта (без железа)
python tools\tx.py bind                 :: «связать» из консоли
python tools\check_receiver_tab.py      :: вкладка «Приёмник»: каналы, бинд, SBUS/CRSF-кодеки
python tests\smoke_test.py              :: 448 проверок, раздел 20 — про живую аппаратуру
```

Железа у стенда нет, поэтому режимы `joystick`/`wire` проверены кодеками и подсказками, а не
живым COM-портом: если пульт не найдётся, скрипт скажет, что включить (`USB Joystick`); для
режима `wire` нужен только `pyserial`.

   * **Через CLI.** Вкладка «Командная строка» → вставьте строки из `vtxtable_example_cli.txt` → `save`.
4. Нажать **Сохранить** внизу вкладки. Таблица запишется в «флеш» и переживёт и

Если передатчик «не поддерживается»: проверьте вкладку «Порты» — на UART4 должна стоять функция
`VTX (TBS SmartAudio)`; после её изменения нужна перезагрузка (прошивка ищет VTX только при старте).

## 2026-09-24 — фичи: биты и порты SOFTSERIAL

В предыдущих сборках биты фич нумеровались подряд, а в прошивке они идут с пропусками.
Из-за этого галочка **SOFTSERIAL** включала в эмуляторе другую фичу, и во вкладке «Порты»
не появлялись строки `SOFTSERIAL1/2`. Исправлено: биты берутся из `featureNames[]` прошивки
(SOFTSERIAL = `1 << 6`, GPS = `1 << 7`, LED_STRIP = `1 << 16`, OSD = `1 << 18`, AIRMODE = `1 << 22`).

Как обновиться:

1. Распаковать новый `bfemu-windows.zip` поверх `C:\bfemu`.
2. **Закрыть окно эмулятора и запустить `run_windows.bat` заново** — иначе работает старый код.
3. В логе при старте не должно быть строки с предупреждением о битах фич.
4. Проверить галочки во вкладке **Конфигурация**: запись, сделанная до обновления, могла включить
   «чужую» фичу (например, GPS вместо SOFTSERIAL). Проще всего выставить нужные галочки заново и
   нажать **Сохранить и перезагрузить**; либо начать с чистого листа: `del C:\bfemu\eeprom.json`.
